# 19 体验闭环设计（发票辅助填入 / 识别指标 / 已办 / 发票硬规则）

> 目标：把「识别结果」真正用到用户流程里，并把识别质量变成可看的数字。
> 范围（对应 `docs/15` §6 的第 4–7 项）：辅助填入、识别指标、我的已办、发票类硬规则。
> 纪律不变：文档先行；识别结果只**预填表单**，不自动写单据；AI/硬规则只出提示，不阻断。

---

## 1. 发票辅助填入（前端）

### 1.1 目标
上传发票 → 异步识别 → 把 `fields[]` 预填进当前明细行（金额/日期/摘要），低置信度字段高亮；用户确认后保存草稿才写库。

### 1.2 交互流程

```
点「上传发票」
  → POST /invoices/upload（multipart）→ 得到 { id, ocrStatus: PENDING }
  → 轮询 GET /invoices/{id}（2s 一次，最多 15 次）
       PENDING/PROCESSING → 显示「识别中…」
       SUCCESS            → 预填字段，显示「已识别（置信度 0.93）」
       MANUAL/FAILED      → 显示「待人工复核 / 识别失败」，不预填
  → 预填只改表单（金额为空才填、日期为空才填、摘要填发票号），不自动保存
```

### 1.3 字段映射（docs/11 §4）

| 识别字段 | 填入明细 | 规则 |
|---|---|---|
| `amount` | `amount` | 仅当明细金额为空；用户手填过的值不覆盖 |
| `invoiceDate` | `expenseDate` | 仅当日期为空 |
| `invoiceCode` + `invoiceNo` | `description` | 拼接成「发票号：xxxx」；已有描述则不覆盖 |
| `fields[].confidence < 0.80` | — | 输入框加 `.input-warn`，并显示「请核对以下字段」 |
| 整单 `MANUAL` | — | 只提示，不预填 |

### 1.4 前端状态（`ReportForm.vue`）

每条明细新增本地态：`invoiceStatus`（PENDING/PROCESSING/SUCCESS/MANUAL/FAILED）、`invoiceConfidence`、`needsReview[]`。
不新增接口；轮询上限 15 次（30s）后停止并提示「识别较慢，可稍后刷新」。

### 1.5 验收
- 上传一张图（mock 下立即 SUCCESS）→ 明细金额/日期/摘要被预填，来源提示可见；
- 手填金额后再次上传同一张图 → 金额不被覆盖；
- 识别失败（构造 FAILED）→ 显示「识别失败，可到发票复核页重试」，不填字段；
- 提交后服务端仍按 `invoiceId` 校验归属（原有逻辑不变）。

### 1.6 发票图片预览（对照识别结果）

**目标**：上传后能直接看到发票图片，和识别出的金额/日期/号码对照，判断识别对不对。

**接口**：复用 `GET /invoices/{id}/file`（Bearer token，返回文件流）；前端 `fetchInvoiceBlobUrl(id)` 转 blob URL。

**表单页（`ReportForm.vue`）**：
- 上传成功即取缩略图（56×56，`object-fit: cover`），点击打开全屏预览（点击遮罩关闭）。
- 识别 `SUCCESS` 后，发票区下方显示一行对照摘要：金额 / 日期 / 发票号；值来自表单，`needsReview` 命中字段标黄。
- 预览 URL 在组件卸载时 `revokeObjectURL`，避免内存泄漏；重新上传时先释放旧 URL。

**复核页（`InvoiceReview.vue`）**：
- 复核弹窗左侧显示发票图片，右侧字段表单；点击图片全屏预览。
- 列表行加「看票」按钮，不进入弹窗也能先看图。

**验收**：
- 上传后缩略图可见，点击可放大；关闭后表单状态不丢；
- 识别成功时对照摘要与表单字段一致，低置信度字段黄色；
- 复核弹窗能看到图片并对照修改；
- 上传 PDF 时不渲染 `<img>`（后端返回 `application/pdf`，提示「PDF 请点开查看」并给下载链接）。

## 2. 识别指标（/admin/metrics）

### 2.1 表结构增量（`invoice`）

| 列 | 类型 | 说明 |
|---|---|---|
| `latency_ms` | `INT DEFAULT NULL` | 单次识别耗时（毫秒），由消费者在 `finish` 时写入；不含排队等待 |

> 为什么不用 `updated_at - created_at`：它包含 MQ 排队与人工复核时间，P95 会失真。

### 2.2 指标口径（并入 `docs/10`）

| 字段 | 口径 |
|---|---|
| `invoiceTotal` | 发票总数（`invoice` 全表，含未识别） |
| `invoiceSuccessRate` | `SUCCESS ÷ invoiceTotal`，2 位小数 |
| `invoiceManualRate` | `MANUAL ÷ invoiceTotal`，2 位小数（人工复核率） |
| `invoiceDegradedRate` | `degraded=1 ÷ invoiceTotal`，2 位小数（主实现可用率的反面） |
| `invoiceP95LatencyMs` | `latency_ms` 的 95 分位（MySQL 8 窗口函数 `PERCENT_RANK`），1 位小数 |

空表一律返回 0，不返回 null（与现有指标一致）。

### 2.3 接口与前端
- `GET /api/v1/admin/metrics` 响应新增上述 5 个字段，不新增接口。
- `AdminView.vue` 总览新增「发票识别」卡片：成功率 / 复核率 / 降级率 / P95 四个数字，并标注「mock 环境数字仅用于演示」。

### 2.4 验收
- 上传 N 张、识别完成后指标变化符合手算；
- 把一张发票置 `degraded=1`，降级率上升；
- 清空 `invoice` 后 5 个字段都是 0，接口不 500。

## 3. 我的已办（审批页 Tab）

### 3.1 目标
审批人能看到「我处理过的节点」，不用翻历史单据。

### 3.2 交互
- `ApprovalTodo.vue` 顶部加 Tab：**待办 / 已办**；切换时重置分页并调对应接口。
- 已办表格列：单号 / 标题 / 申请人 / 级别 / 金额 / 处理时间 / 状态 / 意见；无操作按钮。
- 状态用 `StatusTag kind="node"`（APPROVED/REJECTED/TRANSFERRED）。
- 空态文案区分「没有待办」与「还没有处理记录」。

### 3.3 契约（已实现，`docs/03 §2.3`）
`GET /api/v1/approvals/handled?page=&size=` → `{records:[{approvalId, reportId, reportNo, title, applicantName, amountTotal, stepNo, stepName, status, actedAt, comment}], total, page, size}`。

### 3.4 验收
- 主管通过一条后，待办减少 1、已办出现该条（含意见与处理时间）；
- 已办行可点进详情；
- 非审批角色访问返回 403（后端原有校验）。

## 4. 发票类硬规则（DUPLICATE_*）

### 4.1 规则（`HardRuleEngine`）

| code | 判据 | severity | 文案 |
|---|---|---|---|
| `DUPLICATE_FILE_SUSPECT` | 本单任一发票的 `file_hash` 被**其他上传人**上传过 | HIGH | 「发票文件与其他人上传的重复 N 次，疑似一票多报」 |
| `DUPLICATE_INVOICE_SUSPECT` | 本单任一发票的 `(invoice_code, invoice_no)` 被**其他报销单**使用 | HIGH | 「发票号码 xxx 已被其他报销单使用」 |

### 4.2 保持纯函数
引擎不查库，由调用方把事实查好传进来：

```java
record InvoiceFacts(int invoiceCount, int duplicateFileOtherUploaders, int duplicateInvoiceNoReuse) {}

List<HardFinding> evaluate(report, items, budget, InvoiceFacts facts); // 新增 4 参重载
List<HardFinding> evaluate(report, items, budget);                     // 保留 3 参，facts=null
```

### 4.3 调用方（`AiReviewServiceImpl.runAgent`）
1. 查本单发票（`invoiceMapper` by report_id）；
2. 对每条发票计两个数：
   - `countOtherUploadersByFileHash(fileHash, uploaderId)`；
   - `countOtherReportsByInvoiceNo(code, no, reportId)`；
3. 汇总成 `InvoiceFacts` 传给引擎；结果照旧落 `ai_review.hard_findings` 并进 Agent 上下文。

### 4.4 前端
详情页上一轮已展示 `hardFindings`（红色提示条），无需再改。

### 4.5 验收
- 用另一账号上传同一张图 → 新单的 `hardFindings` 含 `DUPLICATE_FILE_SUSPECT`，审批页可见；
- 同一发票号被两单使用 → 第二单出现 `DUPLICATE_INVOICE_SUSPECT`；
- 规则不阻断提交/审批（单据状态不变）；
- `HardRuleEngineTest` 新增 2 条单测（纯函数、毫秒级）。

### 4.6 索引调整（实现时发现）
- 原 `uk_invoice_no` 唯一键会让"同图跨人上传"在识别回写时直接 `DuplicateKeyException` → `FAILED`，与"交人判断"的设计冲突。
- 改成普通索引 `idx_invoice_no`，重复票号由 `DUPLICATE_INVOICE_SUSPECT` 提示；识别回写仍保留兜底：旧库若还有唯一键，撞键时落 `MANUAL`（`error_msg=DUPLICATE_INVOICE_NO`），不整单失败。

## 6. 边界与不做

- 识别结果**不自动提交**、不自动写 `expense_report`（docs/11 §4 铁律）。
- 指标不引入 Redis 缓存（数据量小，docs/10 §4 已说明）。
- 已办不做导出/批量操作。
- 发票硬规则只在 AI 建议链路产出，不新增审批阻断点。
