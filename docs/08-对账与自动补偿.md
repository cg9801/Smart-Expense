# 08 对账与自动补偿（完整流程）

> 本文是「对账」这条线的唯一设计依据，代码由你实现，我只负责 review 和答疑。
> 关联：`01-表结构.md` §4.6（reconcile_diff）、`02-状态机.md` T4/T6、`04-任务拆解.md` 第 3 周 D4/D5。
> 定稿日期 2026-10-25。

---

## 1. 要解决什么问题

前面所有链路都假设"每步都成功了"，但真实系统一定会有：

- 审批事务提交了，`deduct` 却没执行（历史数据、上线前数据、人工改库）；
- outbox 消息投递到 `DEAD`，付款单永远没建；
- 付款单金额和单据对不上（人工改过、旧版本 bug）；
- 单据状态和时间戳不一致（`APPROVED` 却没有 `finished_at`）。

**对账就是"每天凌晨把所有该对上的数据重新对一遍"，把不一致记下来，能自动修的修掉，不能修的留给人。**

一句话：**对账不产生业务，只负责发现和修复业务数据之间的偏差。**

---

## 2. 三方比对口径（先记住这张表）

| 数据 | 来源 | 判断依据 |
|---|---|---|
| 报销单 | `expense_report` | `status IN ('APPROVED','PAID') AND deleted = 0` |
| 预算实扣 | `budget_txn` | `txn_type='DEDUCT' AND report_id = ?` |
| 付款单 | `payment_order` | `report_id = ?` |
| 消息 | `outbox_message` | `aggregate_type='REPORT' AND aggregate_id = ?` |

**扫描窗口**：`DATE(finished_at) = biz_date`（业务日，默认 T-1）。

为什么不按 `created_at`：一张单可能跨多天审批完，按创建日扫会漏；按"审批完成日"扫，每张单只会进入**一个**批次。

---

## 3. 四类差异（表里已经定死，不要自创）

### 3.1 `BUDGET_NOT_DEDUCTED` —— 该扣的预算没扣

判断：单据 `APPROVED/PAID`，且 `budget_id IS NOT NULL`，但 `budget_txn` 里没有 `DEDUCT:{reportId}`。

自动修复：调用现有的 `budgetService.deduct(report)`。

> **关键**：`deduct` 内部会校验 `frozen_amount >= amount`。
> - 冻结还在（正常情况：审批成功但实扣没执行）→ 补扣成功，`used +金额`、`frozen -金额`；
> - 冻结已经不在了（说明之后又发生过释放）→ `deduct` 抛 40901 → **不要绕过这个守卫**，把差异留成 `OPEN` 转人工。
>
> 绝不能为了"修复"直接 `used += amount`，那是拿钱开玩笑。

### 3.2 `PAYMENT_MISSING` —— 该有的付款单没有

判断：单据 `APPROVED/PAID`，且 `payment_order` 中无 `report_id` 对应行。

自动修复：**走消息链路重放，不直接插付款单**。

```
① 查 outbox_message 是否有该单的 REPORT_APPROVED
   ├─ 有且 status='SENT'  → 消息可能被消费端丢了 → 新增一条新 msg_id 的 NEW 记录重新投递
   ├─ 有但 status IN ('NEW','FAILED') → 直接把 next_retry_at 设为 NOW()，让调度器立刻重试
   ├─ 有但 status='DEAD'  → 重置为 NEW + next_retry_at=NOW()（对账是人工介入后的第二次机会）
   └─ 没有 → 用 OutboxService.append 补写一条 NEW（payload 按单据快照重新拼）
② 等 OutboxRelay 投递 → PaymentConsumer 建单
③ 本轮对账**不等待**消费者完成；差异先标 OPEN，下一轮对账自然消失
```

为什么不直接插付款单：付款单生成逻辑（幂等、单号、事务）全在消费者里，绕过它等于复制一份逻辑，两份迟早不一致。

### 3.3 `AMOUNT_MISMATCH` —— 金额对不上

判断（满足任一）：

- `payment_order.amount != expense_report.amount_total`；
- 存在 `DEDUCT` 流水，但其 `amount != expense_report.amount_total`。

自动修复：**不修**。改钱必须人工，自动改数会把错误掩盖掉。

### 3.4 `STATUS_STUCK` —— 状态和事实自相矛盾

判断（满足任一）：

- `status='APPROVED'` 且 `finished_at IS NULL`；
- `status='PAID'` 且 `paid_at IS NULL`；
- 该单的 `outbox_message` 全部是 `DEAD`（消息已经放弃）。

自动修复：**不修**，转人工。这类问题通常意味着代码路径出了 bug，修数据是治标。

## 4. 对账批次流程

```
POST /admin/reconcile/run?bizDate=2026-10-24（默认昨天）
  1. 建批次：INSERT reconcile_record(biz_date, status='RUNNING')
     └─ uk_biz_date 冲突 → 已有批次：直接返回该批次（幂等，不重跑）
  2. 扫单据：SELECT * FROM expense_report
             WHERE deleted=0 AND status IN ('APPROVED','PAID')
               AND DATE(finished_at) = bizDate
  3. 对每张单做四项检查（§3），命中就写 reconcile_diff
     └─ uk_date_type_report 冲突 → 同一单同类差异已存在：UPDATE detail（保持 OPEN 状态不变）
  4. 对每条新产生的差异尝试自动修复（§5）
  5. 更新批次：scanned_count / diff_count / status='DONE' / finished_at
     └─ 任何未捕获异常 → status='FAILED'，detail 记异常摘要
```

**事务边界**：批次记录本身一个事务；每张单的检查 + 写 diff 一个事务；**每条差异的修复独立事务**。一条修不好不能影响别的。

---

## 5. 自动修复映射

| 差异类型 | 是否自动修 | 修复动作 | 成功判定 |
|---|---|---|---|
| `BUDGET_NOT_DEDUCTED` | ✅ | `budgetService.deduct(report)` | 无异常 → diff 置 `REPAIRED`，`repaired_at=now`，`handler_id=NULL` |
| `PAYMENT_MISSING` | ✅ | 重放/补写 outbox（§3.2） | 补写或重置成功 → `REPAIRED`（付款单由消费者异步补建） |
| `AMOUNT_MISMATCH` | ❌ | — | 保持 `OPEN` |
| `STATUS_STUCK` | ❌ | — | 保持 `OPEN` |

**修复失败**（例如 `deduct` 抛 40901）：diff 保持 `OPEN`，`detail` 追加 `{"repairError":"..."}`，并把该单计入批次 `detail.failures`，**批次仍然 `DONE`**（对账跑完了，只是没修好）。

## 6. 幂等设计（对账最怕重跑）

| 层 | 手段 | 效果 |
|---|---|---|
| 批次 | `uk_biz_date` | 同一天只能有一个批次，重复触发直接返回已有结果 |
| 差异 | `uk_date_type_report` | 同一单同类差异每天一条，重复对账不会刷屏 |
| 补扣 | `budget_txn.uk_biz_no = DEDUCT:{reportId}` | 重复补扣被唯一键挡住 |
| 补建付款单 | 消费者 `mq_consume_log` + `uk_report` | 重放多次仍只有一张单 |
| 重放消息 | 新 `msg_id`（UUID） | 不会和已消费的消息撞幂等键 |

## 7. 人工接口（D5 之后再做，先留位）

| 接口 | 作用 |
|---|---|
| `GET /admin/reconcile/records` | 批次列表（bizDate、扫描数、差异数、状态） |
| `GET /admin/reconcile/diffs?status=OPEN&diffType=...&bizDate=...` | 差异列表，联表带单号/金额 |
| `POST /admin/reconcile/diffs/{id}/repair` | 人工修复：只允许 `OPEN` → `REPAIRED`，记录 `handler_id` |

人工修复也**不能直接改钱**：调用与自动修复相同的服务方法，只是把 `handler_id` 记为操作人。

```

```

依赖注入：`ExpenseReportMapper`、`BudgetTxnMapper`、`PaymentOrderMapper`、`OutboxMessageMapper`、`ReconcileRecordMapper`、`ReconcileDiffMapper`、`BudgetService`、`OutboxService`、`ObjectMapper`。

## 9. 落地顺序（每步可单独验收）

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 两个实体 + 两个 Mapper + 空 Service | 编译通过 |
| 2 | `run()` 只做扫描 + 写批次（不检查差异） | 手动触发后 `reconcile_record` 有 1 行，`scanned_count` 正确 |
| 3 | 四类差异检查 + 写 diff（不修复） | 构造 4 种坏数据，一次跑出 4 条 diff |
| 4 | 自动修复 `BUDGET_NOT_DEDUCTED` | 删掉一条 DEDUCT 流水，跑完 `used` 被补回，diff=`REPAIRED` |
| 5 | 自动修复 `PAYMENT_MISSING` | 删掉付款单 + 把 outbox 改 FAILED，跑完消息重投，付款单回来 |
| 6 | 批次收尾统计 + 失败容错 | 修复抛异常时批次仍 `DONE`，diff 留 `OPEN` 且 detail 有原因 |
| 7 | 定时任务 + 查询接口 | 到点自动跑；`GET /diffs` 能按类型过滤 |

## 10. 构造坏数据的方法（验证专用）

```sql
-- BUDGET_NOT_DEDUCTED：删掉实扣流水（记得先备份）
DELETE FROM budget_txn WHERE report_id = ? AND txn_type = 'DEDUCT';

-- PAYMENT_MISSING：删掉付款单 + 让消息重放
DELETE FROM payment_order WHERE report_id = ?;
UPDATE outbox_message SET status='FAILED', next_retry_at = NOW() WHERE aggregate_id = ?;

-- AMOUNT_MISMATCH：把付款金额改错
UPDATE payment_order SET amount = amount + 1 WHERE report_id = ?;

-- STATUS_STUCK：清掉完成时间
UPDATE expense_report SET finished_at = NULL WHERE id = ?;
```

**做完测试记得还原**：这些改动真实影响数据，测完用事务回滚（集成测试）或手工语句恢复。

---

## 11. 常见坑

1. **按 `created_at` 扫描**：跨天审批的单会漏，或者同一单进多个批次。
2. **直接改 `used_amount` 补扣**：绕过 `frozen` 守卫，钱会凭空多出来。
3. **直接 `INSERT payment_order` 补单**：单号、幂等、审计全部绕过，迟早和消费者逻辑打架。
4. **对账在同一个事务里跑完整批**：一条坏数据让整批回滚，永远修不了。
5. **修复失败把差异标成 `REPAIRED`**：下次对账不再报，问题永久隐身。
6. **重跑同一天产生重复差异**：忘了 `uk_date_type_report`。
7. **对账窗口用 `NOW()` 而不是业务日**：跨零点跑两次会扫到不同数据。

## 12. 面试表述（做完后可用）

> 每天凌晨对 T-1 的已审批单据做三方对账：单据 ↔ 预算实扣流水 ↔ 付款单。按四类差异（缺扣、缺付款单、金额不一致、状态卡死）落 `reconcile_diff`，用 `uk_date_type_report` 保证重复对账幂等。缺扣和缺付款单可自动修复，但修复必须复用业务服务（预算实扣仍走冻结守卫、付款单仍走消息链路），对账只做"发现 + 触发"，不复制写数据的逻辑；金额和状态类差异一律转人工，避免自动改钱。
