# 16 工程经验与踩坑（持续更新）

> 目的：把"下次别再踩"的东西集中放一处。每条都带**现象 → 原因 → 做法**，能直接当 checklist 用。
> 新增经验请追加到对应分类末尾，并在 `docs/15-交接总结.md` §7 留一行索引。

## 1. 文档与事实源

### 1.1 文档会漂移，接口清单≠实现清单
- **现象**：`docs/03` 写着 `DELETE /reports/{id}`、`POST /admin/ai-review/refresh`，代码里根本没有；`README` 还写着 27 个用例和 Thymeleaf。
- **原因**：先写契约后补实现时，只改了代码没回头标状态。
- **做法**：接口清单每一节末尾必须有「实现状态（日期）」；对外数字（用例数、模块数、性能）只能来自当次真实输出。

### 1.2 "没搜到"不等于"没实现"——PowerShell 的 `**` 不递归
- **现象**：用 `Select-String -Path "src\main\java\**\*.java"` 搜 `@Scheduled` 得到空结果，差点误判"定时任务没做"。
- **原因**：Windows PowerShell 的 `**` 只是普通通配，不做递归展开。
- **做法**：`Get-ChildItem -Recurse -Filter *.java | Select-String -Pattern ...`；或直接用 `grep`/`rg` 工具。

### 1.3 文档版本与依赖版本要对齐
- **现象**：`AGENTS.md` 写 Spring Boot 3，`pom.xml` 的 parent 是 4.1.1。
- **做法**：升级框架时，`AGENTS.md`、`README`、`pom`、`docs/04` 四处一起改；以 `pom` 为准，文档跟着走。

## 2. 数据一致性

### 2.1 逻辑删除用 `@TableLogic` + 条件 delete，不要手写 `update deleted=1`
- **现象**：删除草稿要同时完成"鉴权 + 区分状态 + 并发安全"。
- **做法**：实体标 `@TableLogic`，`delete(wrapper)` 会被翻译成带 `deleted=0` 的 UPDATE；wrapper 里再带上 `applicant_id` 与 `status='DRAFT'`，一次 SQL 全搞定。查询侧自动过滤，详情自然 404。

### 2.2 删除不是状态流转
- **做法**：删除只置 `deleted=1`，不进状态机、不写 `expense_status_log`（与建单/编辑一致）。删完解绑发票（`invoice.report_id = NULL`），文件和记录都保留，便于追溯。

### 2.3 JSON 列做去重别用 `LIKE`
- **现象**：超时提醒去重写成 `detail LIKE '%"approvalId":12%'`，同一节点每轮扫描都重复提醒。
- **原因**：MySQL 取 JSON 列会规范化输出（`{"approvalId": 12}` 冒号后带空格），拼字符串对不上。
- **做法**：`CAST(JSON_UNQUOTE(JSON_EXTRACT(detail, '$.approvalId')) AS UNSIGNED) = #{id}`。

### 2.4 表结构变更要同时改 schema 与运行库
- **现象**：预算调整流水没有报销单，但 `budget_txn.report_id` 是 `NOT NULL`。
- **做法**：先改 `sql/schema.sql`（可空），再对现有库执行 `ALTER TABLE ... MODIFY report_id BIGINT UNSIGNED DEFAULT NULL`；只改脚本，老库不会自动变。

## 3. 定时任务与并发

### 3.1 定时任务按"每个节点一个事务"，失败不拖垮整轮
- **做法**：`@Scheduled` 只负责触发；扫描循环里用 `TransactionTemplate` 包住单节点处理，`catch` 后继续下一个。不要给整个扫描方法加 `@Transactional`。

### 3.2 同类自调用 `@Transactional` 不生效
- **现象**：`scanOverdue()` 里直接调 `handleOne()`，`handleOne` 上的 `@Transactional` 不生效。
- **做法**：用 `TransactionTemplate`（本项目做法），或拆到另一个 Spring Bean。

### 3.3 升级"找不到人"时只记日志，不改数据
- **理由**：宁可升级失败、人工可见，也不能把待办置成 SKIPPED 后没人接。数据先保住，再谈自动。

### 3.4 唯一键是最后一道防重复
- 审批节点 `(report_id, step_no, approver_id)` 同时防"重复转交"与"升级插重人"；插之前先查一次，插的时候再靠 `DuplicateKeyException` 兜底并回滚事务。

## 4. 前端

### 4.1 状态文案集中，按钮显隐信后端
- `constants/status.js` 是唯一映射；页面不自己判断"能不能审批"，只认 `availableActions`。
- 付款单状态是另一套（`CREATED/PAID/FAILED`），给 `StatusTag` 加 `kind="payment"`，别混进单据状态。

### 4.2 转账/付款类动作要二次确认
- 付款是终态动作，`window.confirm` 加单号与金额；40901 视为"别人已处理"，关闭弹窗并刷新，不报错。

## 5. 测试

### 5.1 集成测试依赖 seed，断言不要写死姓名以外的环境细节
- 审批链第 2 级取"财务角色 id 最小者"；给测试用户临时加角色会导致断言漂移，测完要还原。
- JSON 列断言用 `contains("approvalId")` + `contains(id)`，别匹配冒号空格。

### 5.2 时间相关断言用相对时间
- SLA 测试用 `LocalDateTime.now().minusHours(...)` 构造超时，不要写死日期，跨天跑也不会坏。

## 6. 异步链路（发票识别）

### 5.1 上传时别沿用旧状态
- **现象**：`InvoiceServiceImpl.upload` 还保留方案 A 的 `MANUAL`，识别消费者永远抢不到 `PENDING`，发票一直是"待复核"。
- **做法**：接入异步链路时，上传必须置 `PENDING`，把状态推进交给消费者；测试会立刻抓到。

### 5.2 业务失败不要 requeue
- **做法**：识别超时/字段缺失是**业务结果**，消费者捕获后落 `FAILED/MANUAL` 并 ack；只有"消息都处理不了"的异常才 nack 进死信。否则 MQ 重投会把一次失败放大成 15 次模型调用。

### 5.3 状态回写必须带条件
- `WHERE ocr_status='PROCESSING'` + `PENDING→PROCESSING` 抢占：重复消息、人工复核、并发重试三者同时存在时，只有第一次生效。

### 5.4 `mq_consume_log.msg_id` 是 32 位
- UUID 去横线正好 32；别加前缀（`"msg-" + UUID` = 40，直接 `Data too long`）。

### 5.5 集成测试别和 MQ 消费者抢跑
- `@SpringBootTest(properties = "spring.rabbitmq.listener.simple.auto-startup=false")` 关监听器，再手动调 `consume`；否则后台消费者和断言竞态，测试时好时坏。

### 6.6 evidence 指向空数组下标 = 理由被删
- **现象**：`ai_review.ai_reasons` 永远是 `[]`，页面只剩 LOW/MEDIUM/HIGH。
- **原因**：mock 的理由写 `evidence: "hardFindings#0"`，但这张单没有硬规则命中 → `hard_findings=[]` → 路径 `0` 越界 → 校验器按"幻觉"整条剔除；LOW 等级本身允许空理由，于是落库成功但没内容。
- **做法**：evidence 要么指向真实存在的路径（`getReportDetail#items.0.amount`），要么指向**整份来源**（`getBudget`，不带 `#`）；mock 演示用后者最稳。
- **另一个坑**：mock 若用调用计数器决定"给工具请求还是给 final"，同进程第二次 runAgent 会直接给 final，但那轮根本没调工具 → evidence 又失效。改成看消息里有没有 `TOOL_RESULT` 才推进。

### 6.7 改完 AI 建议不会自动重算历史单
- **现象**：修好 mock/提示词、重启后端，历史单的详情页还是"暂无 AI 建议"或空理由。
- **原因**：`ai_review` 是**提交时异步算出来的快照**，重启不会回填历史记录；旧记录仍是旧代码的结果。
- **做法**：按单调 `POST /api/v1/admin/ai-review/refresh?reportId=`（仅 ADMIN）重算；批量场景可写个脚本遍历未终态单。新提交的单会自动生成，无需手动干预。

## 7. 构建与环境

### 7.1 pnpm + Windows
- 必须保留 `nodeLinker: hoisted` 与 `store-dir=.pnpm-store`，改回隔离链接会让 Vite 在 Windows 下找不到 esbuild。

### 7.2 验证顺序
1. `mvnw -o test`（87 用例）→ 2. `pnpm build`（49 modules）→ 3. 浏览器全链路（登录→建单→提交→审批→付款→发票复核）。

### 7.3 排障手记（8080/5173 那次）
- **未知异常必须打栈**：`GlobalExceptionHandler` 曾经把一切 `Exception` 吞成 `50001 系统异常`，线上裸奔。已加 `log.error`；`HttpMessageNotReadableException` 单独返回 `40001`（请求体坏是客户端问题，不是系统异常）。
- **PowerShell 下 curl 的 JSON 引号是玄学**：`curl.exe -d "{\"a\":1}"` 在 PS 里会被再加工，发出去可能是 `{\"a\":1}` 或 `{"a":1}`，取决于调用方式。测试接口用 `--data-binary "@body.json"`（写临时文件）最稳，或直接用 `Invoke-RestMethod -Body ($obj | ConvertTo-Json)`。
- **"监听但无响应"= 僵死进程**：`Get-NetTCPConnection` 有监听、HTTP 却连不上，说明进程卡死（常见于 vite 的 esbuild 子进程被限制）。杀掉重启，别怀疑代码。
- **端口归属先看命令行**：`Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"` 看是不是本项目的 java/node，确认后再杀；IDEA 的进程不要碰。
- **HTTP 头不能放中文**：`Content-Disposition: inline; filename="发票.jpg"` 会让 Tomcat 抛 `UnmappableCharacterException` 并移除该头（图片仍返回，但日志刷 ERROR、下载文件名丢失）。用 RFC 5987：`filename*=UTF-8''%E5%8F%91...`（`URLEncoder` + 把 `+` 换 `%20`）。见 `InvoiceController.contentDisposition`。
