# 12 认证与权限（JWT + ThreadLocal 用户上下文）

> 本文是「登录、身份、权限」这条线的唯一设计依据，代码由你实现，我只负责 review 和答疑。
> 关联：`docs/04-任务拆解.md` 第 4 周 D1（原第 1 周欠账）、`docs/03-接口清单.md` §5 错误码、`docs/09-系统架构.md`。
> 定稿日期 2026-10-27。

---

## 1. 现状与要解决的问题

当前所有接口靠请求头 `X-User-Id` 识别用户：

```http
POST /api/v1/reports/{id}/submit
X-User-Id: 1
```

**任何人改一下这个头就能冒充任意用户**，生产不可接受，面试也讲不过去。

本阶段要补：

1. 登录接口，校验用户名密码，签发 JWT；
2. 请求进入时解析 JWT，把当前用户放进 **ThreadLocal 用户上下文**；
3. 业务代码统一从上下文取 `userId`，不再手工读 header；
4. 关键接口做**角色校验**（财务确认付款、管理员对账）；
5. 兼容期开关：`auth.mode=header` 时仍接受 `X-User-Id`，方便已有 curl/测试平滑迁移。

---

## 2. 方案总览

```
POST /auth/login
  ├─ 查 sys_user（status=ACTIVE）
  ├─ BCrypt 校验密码
  ├─ 查角色 sys_user_role + sys_role
  └─ JwtUtil 签发 token（HS256）

业务请求（Authorization: Bearer <token>）
  ├─ JwtInterceptor：解析 → 校验 exp → CurrentUser 写入 UserContext
  ├─ Controller/Service：UserContext.requireUserId()
  ├─ @RequireRole("FINANCE") → 拦截器校验角色
  └─ afterCompletion：UserContext.clear()   ← 必须
```

---

## 3. Token 设计

| 项 | 约定 |
|---|---|
| 算法 | HS256（对称，单服务够用；多服务再换 RS256） |
| Claims | `sub`=userId、`username`、`roles`（数组）、`iat`、`exp` |
| 有效期 | 2 小时（配置 `auth.token-ttl-minutes`） |
| 密钥 | `JWT_SECRET` 环境变量；本地默认值只用于开发，**生产必须替换** |
| 传输 | `Authorization: Bearer <token>`；**不放 URL**（会进日志/Referer） |

JWT 只做**身份声明**，不做权限存储：角色放 claims 只是为了少查库，真正校验以数据库为准（角色变更后旧 token 仍可能带旧角色，过期时间短可接受；严格场景查库）。

## 4. 接口

### 4.1 登录

```http
POST /api/v1/auth/login
Content-Type: application/json

{ "username": "linyi", "password": "123456" }
```

成功：

```json
{
  "code": 0,
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "expiresIn": 7200,
    "user": { "id": 1, "username": "linyi", "realName": "林一", "deptId": 2, "roles": ["EMPLOYEE"] }
  }
}
```

失败：

| 场景 | 返回 |
|---|---|
| 用户名或密码错误 | `40101`「用户名或密码错误」（不区分，防枚举） |
| 用户被禁用 | `40101`「账号不可用」 |
| 参数缺失 | `40001` |

### 4.2 当前用户

```http
GET /api/v1/auth/me
Authorization: Bearer <token>
```

返回同 `user` 结构；无 token/过期 → `40101`。

## 5. 错误码

| 码 | 场景 |
|---|---|
| `40001` | 参数缺失（用户名/密码为空） |
| `40101` | 未登录、token 缺失/过期/签名错误、密码错误 |
| `40301` | 已登录但角色不足 |

> HTTP 状态码：40101 → 401，40301 → 403，由 `GlobalExceptionHandler` 统一映射。

---

## 6. ThreadLocal 用户上下文

```java
public final class UserContext {
    private static final ThreadLocal<CurrentUser> HOLDER = new ThreadLocal<>();
    public static void set(CurrentUser user) { HOLDER.set(user); }
    public static CurrentUser get() { return HOLDER.get(); }
    public static Long requireUserId() { ... 未登录抛 40101 ... }
    public static void clear() { HOLDER.remove(); }   // 必须
}
```

**三条铁律**：

1. `afterCompletion` 里 `clear()`，否则 Tomcat 线程复用会串号；
2. 异步线程（MQ 消费者、定时任务、`@Async`）**没有上下文**，必须显式传 `operatorId`（现有审计已经这么做了）；
3. 不要在 Service 里缓存 `CurrentUser` 到成员变量。

---

## 7. 拦截器与放行规则

| 路径 | 规则 |
|---|---|
| `/api/v1/auth/login` | 放行 |
| `/actuator/**`、静态资源 | 放行 |
| 其余 `/api/**` | 需要 token（`auth.mode=jwt`） |

`auth.mode`：

- `header`（默认，兼容期）：优先解析 token；没有 token 时回退 `X-User-Id`；
- `jwt`：必须有合法 token，`X-User-Id` 一律忽略。

---

## 8. 角色与注解

```java
@RequireRole({"FINANCE", "ADMIN"})
@PostMapping("/{id}/confirm")
public Result<PaymentVO> confirm(...) { ... }
```

拦截器在 `preHandle` 里读方法/类上的注解，与 `CurrentUser.roles` 求交集；为空 → `40301`。

首批加注解的接口：

| 接口 | 角色 |
|---|---|
| `/api/v1/payments/*` | FINANCE / ADMIN |
| `/api/v1/admin/metrics` | ADMIN |
| `/api/v1/admin/reconcile/**` | ADMIN / FINANCE |

---

## 9. 密码

- 存储：BCrypt（`spring-security-crypto` 的 `BCryptPasswordEncoder`，只引 crypto 模块，不启用 Security 过滤链）；
- `seed.sql` 里 `PLACEHOLDER_BCRYPT` 替换为 `123456` 的真实 hash；
- 登录失败不区分「用户不存在 / 密码错误」，统一 `40101`。

## 10. 落地顺序

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 加依赖（jjwt 0.12.6、spring-security-crypto）+ `JwtUtil` | 单测：签发→解析→过期抛异常 |
| 2 | `CurrentUser` + `UserContext` | 单测：set/get/clear，clear 后 get 为 null |
| 3 | `AuthService` 登录 + `/auth/login`、`/auth/me` | curl 登录拿到 token，错误密码 40101 |
| 4 | `JwtInterceptor` + `WebMvcConfig` + `auth.mode` | 无 token 40101；带 token 通过 |
| 5 | Controller 去掉 `@RequestHeader X-User-Id`，改 `UserContext.requireUserId()` | 现有接口用 token 调通 |
| 6 | `@RequireRole` 接到付款/管理接口 | 员工调确认付款 40301 |
| 7 | seed 密码 hash + 文档同步（03/05/README） | 新库可直接登录 |

---

## 11. 验收清单

1. `POST /auth/login` 正确密码 → token；错误密码 → `40101`；
2. 无 token 调 `/api/v1/reports` → `40101`；
3. 带 token 调 `/api/v1/approvals/pending` → 只返回自己的待办；
4. 员工 token 调 `/payments/{id}/confirm` → `40301`；
5. 财务 token 调同一接口 → 成功；
6. 过期 token（把 TTL 调成 1 分钟验证）→ `40101`；
7. 并发请求交替用不同用户 token → 不会串号（ThreadLocal 清理正确）。

---

## 12. 常见坑

1. **忘记 `clear()`**：A 的请求复用线程后读到 B 的身份，最严重的一类 bug；
2. **在异步线程里用 `UserContext`**：MQ 消费者/定时任务永远拿到 null；
3. **把 token 放 URL**：日志、Referer、浏览器历史全部泄露；
4. **密钥写死进代码**：`JWT_SECRET` 必须走环境变量；
5. **登录失败信息太具体**：会暴露用户名是否存在；
6. **只信 claims 里的角色**：角色被撤销后旧 token 仍有权限，敏感接口建议查库或缩短 TTL。

---

## 13. 面试表述

> 认证采用 JWT（HS256，2 小时过期），登录时 BCrypt 校验密码并签发带 userId/roles 的 token；请求经拦截器解析后写入 ThreadLocal 用户上下文，业务层统一取当前用户，`afterCompletion` 强制清理避免线程复用串号；异步消费者不依赖上下文、显式传操作人。权限用方法级注解 `@RequireRole` 控制财务与管理员接口，未认证 401、越权 403。
