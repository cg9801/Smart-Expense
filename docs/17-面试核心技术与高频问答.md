# 17 面试：核心技术与高频问答

> 用法：先背 §1 的一分钟介绍；面试官往哪个方向问，就从 §2 找专题展开；§3 是可直接复述的问答；§4 是"被追问时别慌"的清单。
> 所有数字来自本仓库真实输出：`mvnw test` 92/92、`vite build` 49 modules。没压测过就不说 QPS/P95。

## 1. 一分钟介绍（电梯版）

> 我做了一个智能报销审批系统：员工建单提交后，按「直属主管 → 财务 → 分管」三级审批，提交时冻结部门预算，末级通过转实扣；通过 Outbox + RabbitMQ 异步生成付款单，每日对账自动补偿；审批节点带 SLA，超时先提醒、再超一个 SLA 自动升级；AI 只产出"建议"写独立表，风险只能升不能降，不阻断审批；前端是 Vue3 + Vite 六页加管理后台。
> 重点不是功能多，而是**写操作全部走状态机入口 + 条件更新/唯一键做并发与幂等 + 异步链路用 Outbox 保证不丢 + 对账兜底最终一致**。

## 2. 核心专题

### 2.1 状态机：状态只由状态机改

**做法**：`ReportStateMachine.transit(当前状态, 事件)` 一张流转表校验，非法组合抛 `409 STATE_ILLEGAL`；业务代码禁止 `UPDATE status`，提交/撤回/审批都先算目标状态再条件更新。
**为什么**：状态是最容易写乱的东西；集中一张表后，新增状态只改一处，测试覆盖流转表即可。
**替代方案**：Spring StateMachine（重）、枚举 if-else（会散落）、数据库触发器（不可测）。
**坑**：条件更新必须带 `AND status=旧状态 AND version=old`，否则并发下两个请求都"合法"。

### 2.2 审批链快照：组织调整不影响在途单

**做法**：提交时把「审批人 id/姓名/部门名/级次/SLA deadline」固化进 `expense_approval`，后续只读快照，不再查组织表。
**面试问法**："员工提交后主管离职了怎么办？" → 在途单按快照走，新单才用新组织；离职目标由转交/升级处理。
**坑**：转交插入的新行也要写姓名/部门快照，不能只存 id。

### 2.3 幂等：两个入口两套机制

| 场景 | 机制 |
|---|---|
| 提交 | 请求头 `Idempotency-Key` → `expense_report.submit_token` 唯一索引；冲突回查原单返回 200 |
| 审批/驳回/转交 | `(report_id, step_no, approver_id)` 唯一键 + `WHERE status='PENDING'` 条件更新；影响 0 行按幂等返回当前状态 |
| MQ 消费 | `mq_consume_log(msg_id, consumer)` 联合主键，重复消息直接跳过 |

**面试问法**："用户连点两次提交会两张单吗？" → 不会，同 key 只落一单；不同 key 会生成两单（业务上允许）。

### 2.4 会签/或签与并发

**做法**：先 `SELECT ... FOR UPDATE` 锁住本级所有节点，再更新自己那条，最后统计剩余 `PENDING` 判本级是否完成；或签首个通过后把同级其余置 `SKIPPED`。
**为什么先锁整级**：两个人同时审批，如果各自只锁自己的行，会互相等对方要锁的行 → 死锁；先按 `(step_no)` 锁整级，锁顺序一致。
**坑**：锁内要重读节点，别人可能刚处理完；更新时仍要带 `status='PENDING'`。

### 2.5 转交：改人不改单

**做法**：原行 `PENDING → TRANSFERRED`，插入同 `step_no` 新行（`transfer_from_id` 回指，继承 SLA），单据状态不变。
**防环**：目标不能是本单历史任意审批人（SQL count 判断），否则甲转乙、乙转甲死循环。
**面试问法**："会签中一个人转交了，本级进度重置吗？" → 不重置，已通过节点保持 `APPROVED`。

### 2.6 预算：冻结、实扣、释放、追加

- 提交：`UPDATE dept_budget SET frozen = frozen + ? WHERE total-used-frozen >= ?`，一条 SQL 完成校验与扣减。
- 撤回/驳回：`frozen -= ?`，`WHERE frozen >= ?` 防减成负数。
- 末级通过：`used += ?; frozen -= ?` 同一 SQL 原子转实扣。
- 幂等：`budget_txn.biz_no` 唯一（`FREEZE:{id}:{token}` / `DEDUCT:{id}` / `RELEASE:{id}:{token}`）。
- 调整：`mode=SET/ADD`，追加写 `ADJUST_ADD` 流水；总池约束「本部门新总额 + 其他部门已分配 ≤ 总预算」。
**面试问法**："预算超发怎么防？" → 条件更新把校验写进 WHERE，数据库层面不会出现负数。

### 2.7 Outbox + MQ：消息不丢、不重

**做法**：业务与 `outbox_message` 同事务写入；`OutboxRelay` 每 2s 扫 `NEW`，租约 + 指数退避投递；消费端消费日志幂等 + 付款单唯一键；失败 3 次进死信。
**面试问法**："MQ 挂了会怎样？" → 业务照常提交（消息留在 outbox），恢复后调度器补投；不会丢。
**替代方案**：本地消息表（本项目就是）、事务消息（RocketMQ）、监听 binlog（Canal）。

### 2.8 对账与自动补偿

**做法**：每日扫四类差异——缺扣、缺付款单、金额不一致、状态卡死；能自动修的走幂等接口修，修不了的转 `reconcile_diff` 人工。
**面试问法**："最终一致性怎么证明？" → 对账记录 + 差异表 + 修复后差异清零的测试；故障注入（停 MQ、重复投递）后自愈。

### 2.9 SLA：提醒去重与升级

**做法**：`ApprovalSlaJob` 每 10 分钟扫当前级过期节点：
- 未超 1 个 SLA → 写 `TIMEOUT_REMIND`，同节点 1 小时内去重（JSON 里存 `approvalId`，用 `JSON_EXTRACT` 判断）；
- 超 1 个 SLA → 原节点 `SKIPPED` + 插入新节点，写 `TIMEOUT_ESCALATE`；
- 升级目标：主管级找部门负责人（逐级向上），财务/分管找同角色另一人，兜底 ADMIN；找不到人**只记日志不改数据**。
- 每个节点独立 `TransactionTemplate`，一轮失败不影响其他节点。
**面试问法**："升级会不会改单据状态？" → 不会，只换审批人，状态机约束不受影响。

### 2.10 AI 辅助审核：只建议、不阻断

**做法**：提交事件走 Outbox → `ai-review-consumer` → 硬规则（重复发票、金额不符、超预算）先落库 → Agent 跑模型 → JSON Schema 校验 + `evidence` 白名单 → 风险合并（只能升不能降）→ 写 `ai_review`。
- 建议带 `report_version`，版本不一致标 `STALE`，撤回改单重提后自动重算。
- 审批请求体带 `aiReviewId/aiAdopted`，采纳写审计 `detail`，可统计采纳率。
- 模型挂/超时/非法 JSON 都只影响建议表，审批零影响。
**面试问法**："AI 会不会误判导致错批？" → 建议不阻断、不自动通过，审批人必须显式点通过；风险只能升不能降；`evidence` 只能引用上下文里的数据。
**未实现（要诚实说）**：发票识别异步链路（`InvoiceRecognizer`、复核队列）。

### 2.11 发票：上传、异步识别、复核

**做法**：
- 上传落 `uploads/yyyyMM/uuid.ext`，置 `PENDING` 并**同事务写 Outbox**（`INVOICE_UPLOADED`）；MQ 消费者取件后 `PENDING→PROCESSING` 条件抢占，重复消息不会重复识别。
- 识别器抽象 `InvoiceRecognizer`：`MockInvoiceRecognizer`（默认）、`QwenVlInvoiceRecognizer`（多模态）；`InvoiceRecognizerChain` 按 `primary → fallback` 降级，`degraded` 落库。
- 校验（金额/日期/号码）+ 阈值（整单 < 0.85 转 `MANUAL`）；结果回写带 `WHERE ocr_status='PROCESSING'`，不覆盖人工复核。
- 同人同 `file_hash` 复用不调模型；跨人同 hash 允许上传并标 `duplicateSuspect`（一票多报线索）；`(invoice_code, invoice_no)` 唯一键兜底。
- 复核：`MANUAL` 队列 + `PUT /invoices/{id}/review`（置 `SUCCESS`、`confidence=1.000`）+ `POST /invoices/{id}/retry`（`MANUAL/FAILED` 重新入队，不 requeue 放大调用）。
**没做的**：云 OCR 主实现（接口扩展点已留）、识别指标并入 `/admin/metrics`、识别结果自动预填报销单表单（接口已就绪）。

### 2.12 删除草稿：逻辑删除与边界

**做法**：`@TableLogic` + 条件 delete（`WHERE id AND applicant_id AND status='DRAFT'`），一次 SQL 完成鉴权与并发控制；明细物理删除，发票解绑可复用；不写审计（不是状态流转）。
**面试问法**："删除为什么不用物理删除？" → 可追溯、防误删；查询自动过滤，接口层无感。

### 2.13 前端：Vue3 + Vite

- 请求层 `request.js` 统一解析 `Result`、401 跳登录、错误码透传；状态映射集中 `constants/status.js`；按钮显隐只信后端 `availableActions`，前端不推断状态机。
- 路由守卫 + 后端 `@RequireRole` 双校验；付款页仅 FINANCE/ADMIN。
- 构建产物可挂 Spring Boot `static/` 同源部署（演示只开 8080）。

### 2.14 测试策略

- 集成测试 `@SpringBootTest + @Transactional`，每个用例回滚，不污染演示数据。
- 单测覆盖状态机全表、风控合并、JWT。
- 关键断言：唯一键冲突、并发重复审批、超时升级目标、JSON 列匹配。

## 3. 高频问答（可直接背）

**Q1：为什么用条件更新而不是悲观锁？**
A：单行状态推进用条件更新（`WHERE status=旧值 AND version=旧值`）成本最低，不占连接；只有会签需要"读-判-写"整级时用 `SELECT ... FOR UPDATE`。

**Q2：乐观锁的 version 用在哪？**
A：状态推进、编辑草稿、撤回都带 version；影响 0 行说明别人先改了，返回 409 让前端刷新，而不是静默覆盖。

**Q3：怎么保证审批人只能审自己的节点？**
A：节点归属从上下文用户 id 判断（不信任请求参数），`loadPendingNode` 校验 `approver_id`，不一致 40302。

**Q4：提交时预算不足怎么办？**
A：冻结条件更新失败 → 40902，事务回滚，单据仍是 DRAFT，不落任何状态与流水。

**Q5：Outbox 会不会重复投递？**
A：会，所以消费端必须幂等：消费日志主键 + 付款单 `report_id` 唯一键。

**Q6：对账怎么知道"缺扣"？**
A：单据 APPROVED/PAID 但 `budget_txn` 没有 `DEDUCT` 记录，或用 `used_amount` 与流水求和比对。

**Q7：SLA 升级为什么不动单据状态？**
A：单据状态表达业务阶段，换审批人不改变阶段；混在一起会让状态机爆炸。

**Q8：AI 建议过期怎么处理？**
A：`report_version` 与当前版本比对，不一致返回 `stale=true`；重提后新版本重新生成，旧建议不再展示。

**Q9：prompt injection 怎么防？**
A：发票文本当"待分析数据"处理、截断控制字符、JSON Schema 强约束、`evidence` 白名单（只能引用给定来源）。

**Q10：前端怎么防止越权？**
A：前端路由守卫只是体验；真正的权限在后端方法级 `@RequireRole` + Service 内数据归属校验。

**Q11：为什么不直接物理删除草稿？**
A：逻辑删除可追溯、可审计；配合 `@TableLogic` 查询无感，且能防止误删后数据无法恢复。

**Q12：转交防环为什么必须做？**
A：A 转 B、B 转 A 会无限循环，待办永远关不掉；唯一键也挡不住（step_no 相同但 approver 不同）。

**Q13：预算调整为什么要流水？**
A：调整会改变"已分配"基数，没有流水就无法回答"这个月谁把预算加到了 8 万"；`ADJUST/ADJUST_ADD` 与冻结/扣减流水分开，对账只认后三者。

**Q14：什么时候该拆服务？**
A：现在单体 + 模块边界清晰即可；拆的前提是团队规模与部署频率，不是"显得高级"。

**Q15：如果让你优化性能，先看哪里？**
A：先看索引与慢 SQL（列表过滤、待办排序），再看 AI/发票这类外部调用（异步 + 复用），最后才是缓存。

**Q16：怎么从 mock 切到真实 AI？**
A：两条线各自一个开关——AI 审核设 `AI_PROVIDER=qwen` + `DASHSCOPE_API_KEY`；发票识别设 `INVOICE_QWEN_ENABLED=true`、`INVOICE_RECOGNIZER_PRIMARY=qwen-vl`。接口、状态机、复核队列都不用改，识别器只是换实现。

**Q17：模型挂了 / 超时 / 返回非法 JSON 会怎样？**
A：发票落 `FAILED` 或 `MANUAL`，页面可重试/人工复核；AI 建议落 `FAILED`，审批页显示「暂无 AI 建议」，审批流程零影响。识别失败**不 requeue**，避免 MQ 把一次失败放大成多次调用。

**Q18：怎么控制识别成本？**
A：`file_hash` 复用、单次超时、整单置信度阈值、压测走 mock；每日调用上限是规划项（还没实现，别在简历写）。

**Q19：页面上的 AI 建议为什么只有 LOW/MEDIUM/HIGH，没有具体理由？**
A：建议结构是 `riskLevel + confidence + reasons[]`，只有等级说明 `reasons` 被清空了。最可能的原因是 `evidence` 白名单：理由必须指向真实存在的工具结果或硬规则路径，指到空数组下标（如 `hardFindings#0` 而 `hard_findings=[]`）会被当成幻觉整条剔除。修法：让 evidence 指向真实路径或整份来源，前端渲染 `r.text` 并单独展示 `hardFindings`。

## 5. 白板题（5 分钟）

> 画出"提交 → 审批 → 付款 → 对账"的数据流，标出三个失败点：
> 1. 提交时预算冻结失败（事务回滚）；
> 2. 审批通过后 MQ 挂（outbox 补投）；
> 3. 付款确认重复点击（条件更新 + 唯一键幂等）。
> 每个失败点说清"谁兜底、怎么证明修好了"。

## 6. 这次学到的（自述版）

1. **状态机 + 条件更新是写操作的地基**：先定合法流转，再让每条 SQL 自带校验，并发问题在数据库层就结束。
2. **异步链路的关键不是 MQ，是"业务与消息同事务"**：Outbox 只是把"发消息"降级成"写本地表"。
3. **"建议"和"决策"必须物理隔离**：AI 只写自己的表，审批人显式表态，才敢在简历上写"AI 辅助审核"。
4. **文档先行不是形式**：先写清楚"删除不是状态流转"，代码就不会顺手写错审计。
5. **演示数据必须和真实数据区分开**：mock 识别器固定返回 3200 会让人误以为"OCR 不准"，要标注「演示数据」。

| 8 | 发票预览日志刷 `UnmappableCharacterException` | 中文文件名直接塞 `Content-Disposition` | RFC 5987：`filename*=UTF-8''%E5%8F%91...` |
| 9 | 同图跨人上传识别直接 `FAILED` | `uk_invoice_no` 唯一键把“疑似重复”变成硬失败 | 唯一键改普通索引 + 硬规则 `DUPLICATE_INVOICE_SUSPECT`；识别撞键兜底 MANUAL |
| 10 | 测试时好时坏 | 测试和 MQ 消费者抢跑；测试依赖 seed 冻结金额 | 测试关监听器（`auto-startup=false`）+ 用不存在的预算行构造失败路径 |

### 7.3 性能数字（只读链路，单机）

| 场景 | QPS | P50 | P95 | P99 |
|---|---|---|---|---|
| `GET /reports` 列表 | 270.33 | 10.5ms | 15.3ms | 21.2ms |
| `GET /reports/{id}` 详情 | 270.27 | 25.1ms | 34.4ms | 47.2ms |

**必须主动说清**：单机 + Docker MySQL + 默认 mock + 只读链路；写路径没压；没有缓存。面试官问“能扛多少”，回答“只读 10 并发下 270 QPS，瓶颈在 DB 与详情多次查询，下一步是缓存/索引”，而不是报一个脱离环境的数字。

### 7.4 如果重做，会先做哪三件事

1. **先定接口状态标注规范**（实现/未实现/日期），从第一天起避免文档漂移；
2. **测试隔离从第一天就做**（不依赖 seed、不开监听器），否则后期“时好时坏”很耗人；
3. **AI/识别一律 mock 优先**，真实模型只作为演示开关，先保证业务链路稳，再接模型。

### 7.5 三个可以直接讲故事的点

- **“AI 建议为什么是一张表”**：只建议不决策，采纳率可统计，模型挂了审批不受影响；
- **“为什么发票识别要异步”**：模型 1–5 秒，上传接口不能等；Outbox + 状态机 + 失败不 requeue；
- **“为什么同图跨人能重复上传”**：一票多报是最有价值的检测场景，唯一键会把它藏起来，要用硬规则提示给人。
