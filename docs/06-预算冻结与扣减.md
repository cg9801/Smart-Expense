## 1. 要解决什么问题

报销单**提交时**必须占住部门当月的预算额度，防止同一笔钱被两张单同时花掉；**撤回/驳回时**把额度还回去；**审批通过时**把冻结额度转成实际消耗。

一句话：**预算行上的 `used_amount + frozen_amount` 是唯一的真相，任何变化都必须同时留下一条 `budget_txn` 流水。**

三个动作、三个词：

| 动作 | 业务时机 | 对预算行的影响 | 流水类型 |
|---|---|---|---|
| 冻结 FREEZE | 提交（T1） | `frozen_amount += 金额` | `FREEZE` |
| 释放 RELEASE | 撤回（T2）/ 驳回（T5） | `frozen_amount -= 金额` | `RELEASE` |
| 实扣 DEDUCT | 末级通过（T4） | `used_amount += 金额`、`frozen_amount -= 金额` | `DEDUCT` |

## 2. 数据模型（已有表，不新增）

### 2.1 `dept_budget` 部门月度预算

| 字段 | 含义 |
|---|---|
| `dept_id` | 部门（= 报销单的 `applicant_dept_id` **快照**） |
| `fiscal_year` / `period` | 年度 + `YYYY-MM` 月份 |
| `total_amount` | 总预算 |
| `used_amount` | 已实扣 |
| `frozen_amount` | 在途冻结 |
| `version` | 乐观锁字段，**本项目不启用**（与条件更新二选一，我们选条件更新，见 §6） |

唯一键 `uk_dept_period(dept_id, fiscal_year, period)`：一个部门一个月只有一行。
CHECK `used_amount + frozen_amount <= total_amount`：数据库层兜底，代码写错了也扣不穿。

**可用额度**恒等式：

```
available = total_amount - used_amount - frozen_amount
```

### 2.2 `budget_txn` 预算流水（只追加）

| 字段 | 说明 |
|---|---|
| `budget_id` | 落到哪一行预算 |
| `report_id` | 哪张报销单 |
| `biz_no` | **幂等键**，见 §5.2 |
| `txn_type` | `FREEZE` / `DEDUCT` / `RELEASE` |
| `amount` | 金额，**永远存正数**，方向由 `txn_type` 表达 |

唯一键 `uk_biz_no`：同一个业务动作只能产生一条流水，重复消费天然被拦。

### 2.3 `expense_report` 上的两个字段

- `budget_id`：**第一次冻结时**写入，之后释放/扣减都用它定位预算行；
- `budget_period`：`YYYY-MM`，冻结时的月份快照。

为什么不每次用 `applicant_dept_id + 当前月份` 重新算？因为单据可能跨月还在途、员工可能调部门——**冻结在哪一行，就还到哪一行**，否则额度会“消失在别的月份”。

## 3. 完整生命周期（先看这张图）

```
                       ┌──────────── 提交 T1 ────────────┐
DRAFT ────────────────►│  FREEZE  amount                │──► PENDING / APPROVING
  ▲                    │  frozen += amount              │
  │                    └────────────────────────────────┘
  │                                     │
  │  撤回 T2                             │  末级通过 T4
  │  RELEASE  frozen -= amount           │  DEDUCT  used += amount, frozen -= amount
  │                                     ▼
  └──────────── DRAFT ◄──── PENDING ── APPROVED ──► PAID
                               │
                               │ 驳回 T5
                               │ RELEASE  frozen -= amount
                               ▼
                            REJECTED
```

对应到具体单据（部门 2、2026-10，总额 50000）：

| 时刻 | 单据状态 | `budget_txn` | `frozen` | `used` | `available` |
|---|---|---|---|---|---|
| 初始 | — | — | 0 | 0 | 50000 |
| 提交 1500.50 | PENDING | FREEZE 1500.50 | 1500.50 | 0 | 48499.50 |
| 张三通过 | APPROVING | （无流水） | 1500.50 | 0 | 48499.50 |
| 王五通过 | APPROVING | （无流水） | 1500.50 | 0 | 48499.50 |
| 赵六通过（末级） | APPROVED | DEDUCT 1500.50 | 0 | 1500.50 | 48499.50 |
| 若第 1 级被驳回 | REJECTED | FREEZE + RELEASE | 0 | 0 | 50000 |

**注意两条反直觉的点**：

1. 审批中间级通过时预算**一动不动**，只有末级通过才实扣——因为此时才真正“花出去”；
2. 冻结转实扣时 `available` 不会变化（frozen 减多少、used 加多少），变化的只是“钱的性质”。

## 4. 三个动作的精确步骤

所有动作都在**调用方的事务里**执行（`@Transactional(propagation = REQUIRED)`），失败与调用方一起回滚。

### 4.1 FREEZE（提交时，`ReportServiceImpl.doSubmit` 内）

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 定位预算行：`dept_id = report.applicantDeptId`，`fiscal_year`、`period` 取提交时间 | 提交时间统一用 `now`，不要 `LocalDate.now()` 混用 |
| 2 | 查 `dept_budget`，查不到 → `40902`「未配置部门预算」 | 宁可拒绝提交，也不生成一张没预算的单 |
| 3 | 条件更新余额（见下方 SQL），影响 0 行 → `40902`，message 带可用额度 | 条件更新 = 原子占额度，不需要 `SELECT FOR UPDATE` |
| 4 | 插 `budget_txn(FREEZE, biz_no=FREEZE:{reportId}:{submitToken}, amount)` | 唯一键冲突 → 重复冻结，抛 `40901` 回滚 |
| 5 | 把 `budget.id` / `period` 返回给调用方，写进 `expense_report.budget_id / budget_period` | 与单据状态更新在**同一条 UPDATE** 里完成 |

冻结的 SQL：

```sql
UPDATE dept_budget
SET frozen_amount = frozen_amount + ?
WHERE id = ?
  AND total_amount - used_amount - frozen_amount >= ?;
```

`>=` 用参数传入同一个金额，**不要用 `SET ... WHERE frozen + ? <= total` 的变体**——两者等价，但前者能直接用上 `CHECK` 约束的语义。

### 4.2 RELEASE（撤回 T2 / 驳回 T5）

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | `report.budget_id` 为空 → 直接返回（历史数据/预算功能上线前的单） | 释放必须可空转，不能因为老数据炸掉撤回 |
| 2 | 条件更新：`frozen_amount -= 金额 WHERE id=? AND frozen_amount >= 金额`，0 行 → `40901`（说明重复释放或数据不一致） | 用 `>=` 防负数 |
| 3 | 插 `budget_txn(RELEASE, biz_no=RELEASE:{reportId}:{submitToken})` | 撤回后重提会产生新的 submitToken，所以每次都能冻结/释放一次 |

### 4.3 DEDUCT（末级通过 T4，`ApprovalServiceImpl.approve` 第 8 步内）

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | `report.budget_id` 为空 → 直接返回（兼容历史单） | |
| 2 | 条件更新：`used_amount += 金额, frozen_amount -= 金额 WHERE id=? AND frozen_amount >= 金额`，0 行 → `40901` 回滚（单据状态也不会变） | 一次 SQL 同时改两个字段，保证“转性质”原子 |
| 3 | 插 `budget_txn(DEDUCT, biz_no=DEDUCT:{reportId})` | 通过是终态，一单只会扣一次，不需要 token |
| 4 | 之后写审计、返回详情 | 审计仍放最后 |

实扣的 SQL：

```sql
UPDATE dept_budget
SET used_amount = used_amount + ?,
    frozen_amount = frozen_amount - ?
WHERE id = ?
  AND frozen_amount >= ?;
```

### 4.4 调用点一览（改哪几个文件）

| 动作 | 调用方 | 调用时机 |
|---|---|---|
| `freeze` | `ReportServiceImpl.doSubmit` | 审批链快照之后、单据 UPDATE 之前；返回值用于 `.set(budgetId)` |
| `release` | `ReportServiceImpl.withdrawReport` | 单据状态更新成功之后、审计之前 |
| `release` | `ApprovalServiceImpl.reject` | 节点/单据更新之后、审计之前 |
| `deduct` | `ApprovalServiceImpl.approve` | 末级分支、单据 UPDATE 之后、审计之前 |

**顺序原则**：预算动作放在“单据状态已经确认能改成功”之后（freeze 除外，它要拿 `budget_id`），这样条件更新失败时不会先动预算。

## 5. 幂等、并发、失败

### 5.1 三层保护

| 层 | 手段 | 挡住什么 |
|---|---|---|
| 提交入口 | `expense_report.submit_token` 唯一索引 | 同一个 `Idempotency-Key` 重复提交 |
| 预算余额 | `UPDATE ... WHERE available >= amount` 条件更新 | 并发超支、重复冻结 |
| 流水 | `budget_txn.uk_biz_no` 唯一索引 | 同一业务动作重复记账（重试、MQ 重复投递） |

### 5.2 `biz_no` 命名规则（本项目的约定）

| 动作 | 格式 | 例 |
|---|---|---|
| 冻结 | `FREEZE:{reportId}:{submitToken}` | `FREEZE:1:demo-201` |
| 释放 | `RELEASE:{reportId}:{submitToken}` | `RELEASE:1:demo-201` |
| 实扣 | `DEDUCT:{reportId}` | `DEDUCT:1` |

为什么冻结要带 `submitToken`：**撤回后重新提交是同一张单的第二次冻结**，只用 `reportId` 会撞唯一键，第二次提交永远失败。`submitToken` 每次提交都不同（也正好是提交幂等的键），天然区分“第几次提交”。

### 5.3 并发场景推演

**场景 A：同一张单被两个请求同时提交。**
两个事务都通过 `submit_token` 检查（还没插），随后都尝试冻结。第一个把 `frozen` 加上并插流水成功；第二个的 `submit_token` 唯一索引冲突（或预算条件更新/流水唯一键冲突）→ 整个事务回滚，预算恢复。**净效果只冻结一次。**

**场景 B：部门预算只剩 1000，两张 800 的单同时提交。**
两个 `UPDATE ... WHERE available >= 800` 都到达数据库，InnoDB 行锁让它们串行：第一个成功（available 剩 200），第二个条件不满足 → 0 行 → `40902`。**不会超支。**

**场景 C：末级审批与撤回并发。**
撤回要求“全部节点 PENDING”，末级审批会先把节点改掉，撤回的条件更新/节点检查会失败回滚；反之审批也会因为单据已是 DRAFT 而条件更新 0 行回滚。预算动作都挂在事务里，跟着一起回滚。

**场景 D：同一条 MQ 消息投递两次（第 3 周做）。**
第二次 `DEDUCT:{reportId}` 撞 `uk_biz_no` → 消费端捕获并丢弃。这是把唯一键当消费幂等的主要原因。

### 5.4 失败矩阵

| 情况 | 返回 | 事务 |
|---|---|---|
| 部门未配置当月预算 | `40902` | 提交整体回滚，单据仍是 DRAFT |
| 可用额度不足 | `40902`（message 带 available） | 同上 |
| 冻结流水唯一键冲突 | `40901`「预算已冻结」 | 回滚 |
| 释放时 `frozen < amount` | `40901`「预算数据不一致」 | 回滚 |
| 实扣时 `frozen < amount` | `40901` | 回滚，单据不会变 APPROVED |
| `budget_id` 为空（历史单） | 跳过，正常返回 | 正常提交 |

## 6. 为什么不加 `SELECT ... FOR UPDATE`

- 条件更新本身就是“读-判断-写”的原子组合，`WHERE available >= amount` 由 InnoDB 在行锁保护下求值；
- 少一次查询、少一次显式锁，也少一类死锁；
- 预算行与单据行、审批节点行之间不需要交叉加锁，只要**保证同一事务内按固定顺序**（先节点/单据，后预算）就不会互相等。

`version` 字段保留但不用：一个业务规则只允许一种并发控制手段，混用时排查会非常痛苦。

## 9. 常见坑

1. **用当前月份去还额度**：跨月撤回会把 9 月的冻结还到 10 月，必须用 `report.budget_id`。
2. **只改余额不写流水**：对账时无法解释余额变化，等于把账做丢了。
3. **先写流水再改余额但不校验影响行数**：额度不足时流水已经落库，事务一提交就是假账。必须检查 `rows == 0` 并抛异常。
4. **释放时忘了 `frozen >= amount`**：重复释放会把 `frozen` 减成负数，CHECK 约束会拦，但报错信息很难懂。
5. **`biz_no` 只用 reportId**：撤回重提第二次冻结必然撞唯一键。
6. **把预算动作写成独立事务**（`REQUIRES_NEW`）：提交失败时预算却冻上了，形成“幽灵冻结”。
7. **并发测出来没问题就以为对**：单线程测试测不出条件更新的价值，必须用两个并发请求验证。

## 10. 并发验证记录（2026-10-25 实测）

单 JVM（Tomcat 8082）+ MySQL 8，用 8 个并发请求在**同一时刻**打接口（各请求先等到同一时间点再发）。

| 场景 | 操作 | 结果 | 结论 |
|---|---|---|---|
| A. 同一节点重复审批 | 同一 `approvalId` 并发 8 次 `POST /approve` | HTTP `200 ×1`、`409 ×7`；节点 `APPROVED` 一次；`APPROVE` 审计仅 1 条；单据只推进一级 | 锁整级 + `WHERE status='PENDING'` 条件更新生效 |
| B. 预算并发争抢 | 可用额度 3000，两张 2500 的单同时提交 | `200 ×1`、`40902 ×1`；败者仍 `DRAFT`、无审批链、无流水；`frozen` 仅 +2500；`budget_txn` 仅 1 条 | 条件更新 `available >= amount` 原子占额度，不超支 |
| C. 重复提交同一单 | 同一单、同一 `Idempotency-Key` 并发 2 次 `POST /submit` | `200 ×2`（一次真提交、一次幂等回放）；审批链 3 行；`SUBMIT` 审计 1 条；`FREEZE` 流水 1 条 | `uk_submit_token` + 幂等回放生效 |

> 局限：本机单 JVM，未覆盖多实例 + MQ 重复投递；后者由 `budget_txn.uk_biz_no` 与 `mq_consume_log` 兜底（第 3 周实现）。会签 `AND` / 或签 `OR` 的并发未实测（当前审批链固定 `SINGLE`）。
