# 03 接口清单

> Base URL：`/api/v1`；所有接口返回统一结构；写操作携带 `X-Trace-Id`（缺省由网关注入）。
> 权限码：`EMPLOYEE` / `SUPERVISOR` / `FINANCE` / `DIRECTOR` / `ADMIN`。

## 1. 通用约定

### 1.1 统一响应

```json
{ "code": 0, "message": "ok", "data": {}, "traceId": "8f3a1c" }
```

- `code = 0` 成功；非 0 见 §5 错误码，HTTP 状态码同时表达语义（400/401/403/404/409/429/500）。
- 分页数据固定为 `{ "records": [], "total": 0, "page": 1, "size": 20 }`。
- 时间格式 `yyyy-MM-dd HH:mm:ss.SSS`（东八区），日期 `yyyy-MM-dd`，金额为字符串或两位小数数值。

### 1.2 幂等与并发

| 场景 | 机制 |
|---|---|
| 提交报销单 | 请求头 `Idempotency-Key: <uuid>`，服务端写入 `expense_report.submit_token` 唯一索引；重复请求返回原单据（200） |
| 审批/驳回/转交 | 依赖唯一键 `(report_id, step_no, approver_id)` + `WHERE status='PENDING'` 条件更新；重复请求返回当前状态（200） |
| 状态冲突 | 条件更新影响行数为 0 → `409 / 40901`，响应体带当前 `status`，前端提示刷新 |
| 预算不足 | 冻结条件更新失败 → `409 / 40902`，不落任何单据状态 |

> **2026-10-31 追加**：`PUT /reports/{id}`（编辑草稿，仅本人 + `DRAFT`，明细整体替换、金额按明细重算）与 `GET /reports/{id}/timeline`（审计回放，正序，`detail` 原样返回 JSON 字符串）已实现。
> **2026-10-31 追加（删除）**：`DELETE /reports/{id}` 已实现（`ReportServiceImpl.deleteDraft`）：仅本人 + `DRAFT`，逻辑删除（`deleted=1`）；明细物理删除、发票解绑（可复用）。删除**不是状态流转**，不写审计。创建/编辑草稿本身也不写审计，`timeline` 只出现真实的流转动作（提交/审批/转交/提醒/升级/撤回）。

**提交请求**

```http
POST /api/v1/reports/1001/submit
Idempotency-Key: 5b1e0c4e-9f3a-4c1e-8b7d-2f0a9c6d1e33
```

  "code": 0,

### 2.3 审批

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/approvals/pending` | 我的待办：`page`、`size`，按 `deadline_at` 升序 | 审批人 |
| GET | `/approvals/handled` | 我的已办：`page`、`size`，按 `acted_at` 倒序，含 `comment` | 审批人 |
| GET | `/approvals/transfer-candidates` | 转交候选人：`reportId` 可选，返回在职、非本人、非本单历史审批人 | 审批人 |
| POST | `/approvals/{approvalId}/approve` | 通过，`comment` 可选 | 节点审批人 |
| POST | `/approvals/{approvalId}/reject` | 驳回，`comment` **必填** | 节点审批人 |
| POST | `/approvals/{approvalId}/transfer` | 转交，`targetUserId` + `comment` | 节点审批人 |

**审批请求/响应**

```json
{ "comment": "行程与发票一致，同意" }
```

```json
{
  "code": 0,
  "data": { "reportId": 1001, "reportStatus": "APPROVING", "currentStep": 2, "stepPassed": true },
  "traceId": "8f3a1c"
}
```

- 会签同级未批完时返回 `stepPassed: false`，`reportStatus` 保持 `APPROVING`。
- 非本人节点 → `403 / 40302`；节点已处理 → 幂等返回当前状态，不报错。

**转交实现说明（2026-10-31）**：`POST /approvals/{approvalId}/transfer` 已实现（`ApprovalServiceImpl.transfer`）。行为：原节点 `PENDING → TRANSFERRED`，插入同 `step_no` 的新 `PENDING` 节点（`transfer_from_id` 指回原行，继承 SLA 与来源角色）；单据状态不变。守卫：目标存在且在职、不能转给自己、**目标不得为本单历史审批人**（防环，`docs/02` §5）。请求体 `{ "targetUserId": 3, "comment": "..." }`，`comment` 选填。
>
> **已办与候选人（2026-10-31 追加）**：`GET /approvals/handled` 返回 `APPROVED/REJECTED/TRANSFERRED` 节点（`actedAt`、`comment`）；`GET /approvals/transfer-candidates?reportId=` 返回 `{userId, realName, deptName}[]`，SQL 层直接排除本人与该单历史审批人，前端只负责展示，服务端 `transfer` 仍会再校验一次防环。前端转交弹窗已改为下拉选人。

> **追加流水（2026-10-31 追加）**：`PUT /budgets/{deptId}` 支持 `mode`：`SET`（默认，覆盖）或 `ADD`（追加，`totalAmount` 是增量）。两种模式都写 `budget_txn`（`ADJUST` / `ADJUST_ADD`，金额为本次变化量），`report_id` 允许 NULL；对账只认 `FREEZE/DEDUCT/RELEASE`，调整流水仅用于审计回放。

### 2.5 发票（v2）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/invoices/upload` | 上传（multipart），落库后投递识别 MQ，立即返回 `PENDING`；同人同 `file_hash` 直接返回已有记录（不重复调模型） | EMPLOYEE |
| GET | `/invoices/{id}` | 识别状态 + 结构化结果 + **字段级置信度**（`fields[].confidence`、`needsReview[]`、`recognizer`、`degraded`） | 本人/财务 |
| GET | `/invoices` | `ocrStatus=MANUAL` 拉取人工复核队列 | FINANCE |
| PUT | `/invoices/{id}/review` | 人工复核：修正金额/日期/号码并置 `SUCCESS` | FINANCE |
| POST | `/invoices/{id}/retry` | 重新触发识别（`MANUAL` / `FAILED` 时可用） | FINANCE/ADMIN |

> 识别器抽象、降级链、重复上传的三种情形、重试边界（识别失败不在 MQ 层重投）见 [11-AI识别与辅助审核.md](11-AI识别与辅助审核.md) §3。

**实现状态（2026-10-31，识别链路已接入）**：`POST /invoices/upload`、`GET /invoices/{id}`、`GET /invoices/{id}/file`、`GET /invoices`（复核队列）、`PUT /invoices/{id}/review`、`POST /invoices/{id}/retry` 均已实现：
- 上传：multipart 字段 `file`（图片/PDF，≤10MB），文件落 `app.upload.dir`（默认 `uploads/`），上传后置 `PENDING` 并**同事务写 Outbox**（`INVOICE_UPLOADED`），由 `InvoiceRecognizeConsumer` 异步识别（`PENDING → PROCESSING → SUCCESS/MANUAL/FAILED`）。
- **同人同 `file_hash` 直接复用**（`docs/11` §3.4 情形 1）；**跨人同 hash 允许上传**（索引改为 `(uploader_id, file_hash)`），返回 `duplicateSuspect=true` 提示疑似一票多报（情形 2）。
- 识别：`InvoiceRecognizer` 抽象 + `InvoiceRecognizerChain`（`primary → fallback` 降级），默认 `mock`；真实多模态见 [18-接入真实AI.md](18-接入真实AI.md)。结果回写带 `WHERE ocr_status='PROCESSING'`，重复消息不覆盖人工复核。
- 复核：`GET /invoices?ocrStatus=MANUAL` 分页队列（FINANCE/ADMIN）；`PUT /invoices/{id}/review` 修正字段并置 `SUCCESS`（confidence=1.000）；`POST /invoices/{id}/retry` 仅 `MANUAL/FAILED` 可用，重新置 `PENDING` 并投递。
- 详情扩展：`fields[].confidence`、`needsReview[]`、`recognizer`、`degraded`、`retryCount`、`duplicateSuspect`。

## 3. 关键语义

1. **查询详情返回可用动作**：`availableActions: ["WITHDRAW"]`，前端不自行推断状态机，避免两边规则漂移。
2. **列表过滤在 SQL 完成**：`scope=mine` 按 `applicant_id`，`scope=dept` 按部门（主管），避免全量拉取后内存过滤。
3. **大字段裁剪**：详情接口默认不返回 `model_result` 等原始 JSON，仅 `?withRaw=true` 时返回。
4. **并发审批**：会签场景同一级多人同时提交，服务端以行锁+条件更新串行化，客户端不需要额外协调。

## 5. 错误码

| code | HTTP | 含义 | 处理建议 |
|---|---|---|---|
| 0 | 200 | 成功 | — |
| 40001 | 400 | 参数校验失败 | 返回字段级错误 |
| 40101 | 401 | 未登录/Token 过期 | 跳登录 |
| 40301 | 403 | 无角色权限 | 提示无权限 |
| 40302 | 403 | 不是当前节点审批人 | 刷新待办 |
| 40401 | 404 | 单据/任务不存在 | 返回列表 |
| 40901 | 409 | 当前状态不允许该操作 | 返回最新状态，提示刷新 |
| 40902 | 409 | 预算不足 | 显示可用额度 |
| 40903 | 409 | 幂等键已用于不同内容 | 换新 `Idempotency-Key` |
| 42901 | 429 | 提交过于频繁 | 稍后重试 |
| 50001 | 500 | 系统异常 | 带 `traceId` 反馈 |
