# 05 工程结构

> 代码根：`Smart-Expense/src/main/java/com/occ/smartexpense/`

## 1. 分层与依赖方向

```
controller ──► service（接口）──► service.impl ──► mapper ──► entity ──► MySQL
                    │                    │
                    │                    ├── dto（入参，controller 传入）
                    └────────────────────┴── vo （出参，controller 返回）
```

依赖只能单向：Controller 只依赖 Service 接口；ServiceImpl 依赖 Mapper；DTO/VO 不依赖任何业务类。
Entity 只在 Service/Mapper 内部流转，**不直接返回给前端**。

## 2. 包职责

| 包 | 放什么 | 禁止放什么 |
|---|---|---|
| `controller` | HTTP 入口：接收/校验参数、调用 Service、包装 `Result` | 业务判断、SQL |
| `service` | 业务接口，只声明"做什么" | 实现细节、HTTP 对象 |
| `service.impl` | 事务边界、业务校验、状态机调用、DTO↔Entity↔VO 转换 | `HttpServletRequest` 等 web 对象 |
| `mapper` | `BaseMapper<T>` + 复杂 SQL（XML 在 `resources/mapper/**/*.xml`） | 业务判断 |
| `entity` | 表映射（`@TableName`），与 `sql/schema.sql` 一一对应 | 对外暴露 |
| `dto` | 入参对象，带 `jakarta.validation` 注解 | 出参字段 |
| `vo` | 出参对象，带 `@JsonFormat` 等序列化配置 | 入参校验 |
| `common` | `Result`、`ErrorCode`、`BizException`、`GlobalExceptionHandler` | 业务逻辑 |
| `enums` | 状态与事件枚举（`ReportStatus`、`ReportEvent`） | SQL、HTTP |
| `statemachine` | 状态流转表与合法性校验（`ReportStateMachine`），唯一判定流转的地方 | SQL、事务、HTTP |

## 3. 命名与约定

- 类后缀：`XxxController` / `XxxService` / `XxxServiceImpl` / `XxxMapper` / `XxxDTO` / `XxxVO`。
- 表名转实体：`expense_report` → `ExpenseReport`（下划线转驼峰由 MyBatis-Plus 配置处理）。
- 统一响应 `{code, message, data}`，错误码见 `docs/03-接口清单.md §5`。
- MySQL 连接、MyBatis-Plus 配置在 `src/main/resources/application.yaml`。
- 复杂查询写 XML；简单 CRUD 用 `BaseMapper`，不写重复 SQL。
- **方法命名三处一致**：Controller 调用处 = Service 接口 = ServiceImpl 实现；Controller 处理方法与 Service 同名（如 `createDraft`）。

## 5. 审批动作实现步骤（定稿，不再变更）

> 本节是审批通过/驳回的**唯一实现依据**。代码必须与本节步骤顺序一致；后续如需调整，只能在本节追加"变更记录"并说明原因，不得在代码里另起一套顺序。
> 状态语义见 `docs/02-状态机.md` §3（T3/T4/T5）与 §4（节点状态）。

### 5.1 签名与接口（锁死）

| 项 | 定稿 |
|---|---|
| Service 接口 | `ReportDetailVO approve(Long approvalId, Long userId, String comment)` |
| | `ReportDetailVO reject(Long approvalId, Long userId, String comment)` |
| Controller | `POST /api/v1/approvals/{approvalId}/approve`、`POST /api/v1/approvals/{approvalId}/reject` |
| 请求头 | `X-User-Id` 必填，缺失 → `40001` |
| 请求体 | `ApprovalActionDTO { @Size(max = 512) String comment }`，驳回时 `comment` 必填（Service 校验） |
| 响应 | `Result<ReportDetailVO>`（与 `GET /pending` 一致） |
| 事务 | 两个方法都标 `@Transactional(rollbackFor = Exception.class)` |

### 5.2 `approve` 八步（顺序不可调换）

| 步 | 动作 | 失败返回 |
|---|---|---|
| 1 | `selectById(approvalId)` 取节点 → 不存在 | `40401` |
| 2 | 校验 `approverId == userId` | `40301` |
| 3 | **先锁本级**：按 `reportId + stepNo` 查同一级全部节点，末尾 `FOR UPDATE` | — |
| 4 | 从第 3 步结果里取自己那条，`status != PENDING` | `40901` |
| 5 | 条件更新自己那条：`WHERE id=? AND status='PENDING'`，置 `APPROVED`、`acted_at=now()`、`comment`；影响 0 行 | `40901` |
| 6 | `judgeStepPassed(mode, stepNodes, currentId)`：`CANCELLED/TRANSFERRED/SKIPPED` 不参与；`SINGLE`=本人已通过；`AND`=非空且全部通过；`OR`=任一通过 | — |
| 7 | 未通过 → 写审计 `APPROVE`（`APPROVING→APPROVING`，detail 记 stepNo/approvalId）→ 返回详情 | — |
| 8 | 通过 → 推进单据（见 5.4）→ 写审计 → 返回 `reportService.getDetail(reportId)` | `40901` |

> 第 3 步必须在第 5 步之前：先 `UPDATE` 自己那行再锁整级，两个同级审批人并发时会各自持有对方要锁的行 → 死锁。锁顺序统一为「整级 → 自己」。

### 5.3 `reject` 七步

| 步 | 动作 | 失败返回 |
|---|---|---|
| 1 | `comment` 为空/空白 | `40001` |
| 2 | 同 5.2 第 1–4 步（取节点、校验归属、锁本级、复核 `PENDING`） | 对应错误码 |
| 3 | 状态机校验：`stateMachine.transit(APPROVING, REJECT)` 必须成功 | `40901` |
| 4 | 条件更新自己那条：`WHERE id=? AND status='PENDING'`，置 `REJECTED`、`acted_at`、`comment`；0 行 | `40901` |
| 5 | 该单其余 `PENDING` 节点全部置 `CANCELLED`（按 `report_id` 过滤，**不限于本级**） | — |
| 6 | 条件更新单据：`WHERE id=? AND status IN ('PENDING','APPROVING')`，置 `REJECTED`、`finished_at=now()`；0 行 | `40901` |
| 7 | 写审计 `REJECT`（`APPROVING→REJECTED`，detail 记 stepNo/approvalId/comment）→ 返回详情 | — |

### 5.4 通过后的"推进单据"分支（5.2 第 8 步展开）

1. 读 `expense_report`，得 `totalSteps`、`status`。
2. `lastStep = (stepNo == totalSteps)`。
3. 条件更新单据，两条分支共用一个 `WHERE id=? AND current_step=? AND status IN ('PENDING','APPROVING')`（第 1 级审批时单据仍是 `PENDING`，只写 `='APPROVING'` 会误判 40901），影响 0 行 → `40901` 并回滚：
   - **非末级**：`current_step = stepNo + 1`，`status` 不变。
   - **末级**：`status='APPROVED'`，`finished_at=now()`，`current_step` 不变。
4. 审计 `APPROVE`：非末级 `APPROVING→APPROVING`（第 1 级时是 `PENDING→APPROVING`），末级 `APPROVING→APPROVED`（第 1 级即末级时是 `PENDING→APPROVED`）。
5. 同级节点收尾：仅 `OR`（或签）模式下，本级其余 `PENDING` 节点置 `SKIPPED`；`SINGLE` 无同级他人、`AND` 会签不动。

### 5.5 审计（`expense_status_log`）

- **一次请求只写一条**，`from_status/to_status` 记**单据级**状态，`detail` 记 `{"stepNo":n,"approvalId":id}`（驳回再加 `comment`）。
- 节点级状态变化靠 `expense_approval.status` 自证，不再额外双写，避免一条请求两条日志。

### 5.6 错误码对照

| 场景 | 码 |
|---|---|
| 缺 `X-User-Id`、驳回缺 `comment` | `40001` |
| 节点不属于当前用户 | `40301` |
| 节点不存在 | `40401` |
| 节点已处理 / 单据已推进 / 状态机不合法 | `40901` |
