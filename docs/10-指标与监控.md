# 10 指标与监控

> 本文是「运营指标接口」的唯一设计依据：先读完再写代码。
> 关联：`docs/03-接口清单.md` §2.6、`docs/04-任务拆解.md` 第 4 周 D7、`docs/09-系统架构.md` §1。
> 定稿日期 2026-10-27。

---

## 1. 要解决什么问题

系统跑起来之后，需要一眼看到「业务健不健康」：

- 提交了多少单、通过率多少、审批要多久；
- 有多少付款单还没付；
- 对账有多少差异没处理；
- 有没有消息投递失败到 `DEAD`。

没有指标，这些只能靠人肉写 SQL。所以做一个只读接口，把这些数字聚合成一个 JSON，给管理页/演示页用。

**一句话：指标接口不写业务数据，只把现有表算成数字。**

## 3. 指标定义与口径

| 字段 | 含义 | 口径 |
|---|---|---|
| `submitCount` | 累计提交单数 | `expense_report` 中 `submit_token IS NOT NULL AND deleted = 0` |
| `approvedCount` | 已通过单数 | `status IN ('APPROVED','PAID')` |
| `rejectedCount` | 已驳回单数 | `status = 'REJECTED'` |
| `approveRate` | 审批通过率 | `approved / (approved + rejected)`，保留 2 位小数 |
| `avgApprovalHours` | 平均审批耗时（小时） | `AVG(TIMESTAMPDIFF(MINUTE, submitted_at, finished_at)) / 60`，保留 1 位小数 |
| `paymentPending` | 待付款单数 | `payment_order.status = 'CREATED'` |
| `reconcileOpenDiffs` | 待处理差异数 | `reconcile_diff.status = 'OPEN'` |
| `outboxDead` | 投递放弃的消息数 | `outbox_message.status = 'DEAD'` |

**口径约定**：

- 所有单据统计都要带 `deleted = 0`（逻辑删除）；
- `approvedCount` 把 `PAID` 也算进去，因为「付过款」必然「通过过」；
- 通过率的分母是「已出结果」的单（通过 + 驳回），不是全部提交单——在途单不该拉低通过率；
- 平均耗时只统计 `finished_at IS NOT NULL` 的单；
- 没有数据时返回 `0`，不返回 `null`。

## 4. 数据来源与 SQL

全部来自现有表，**不新增表、不新增 Redis 结构**。

```sql
-- submitCount
SELECT COUNT(*) FROM expense_report
WHERE deleted = 0 AND submit_token IS NOT NULL;

-- approvedCount
SELECT COUNT(*) FROM expense_report
WHERE deleted = 0 AND status IN ('APPROVED','PAID');

-- rejectedCount
SELECT COUNT(*) FROM expense_report
WHERE deleted = 0 AND status = 'REJECTED';

-- avgApprovalHours（在 Java 里除 60，保留 1 位）
SELECT AVG(TIMESTAMPDIFF(MINUTE, submitted_at, finished_at))
FROM expense_report
WHERE deleted = 0
  AND submitted_at IS NOT NULL
  AND finished_at IS NOT NULL
  AND status IN ('APPROVED','PAID','REJECTED');

-- paymentPending
SELECT COUNT(*) FROM payment_order WHERE status = 'CREATED';

-- reconcileOpenDiffs
SELECT COUNT(*) FROM reconcile_diff WHERE status = 'OPEN';

-- outboxDead
SELECT COUNT(*) FROM outbox_message WHERE status = 'DEAD';
```

前五条里只有「平均耗时」需要聚合函数，写在 `ExpenseReportMapper` 里用 `@Select`；其余用 MyBatis-Plus 的 `selectCount(wrapper)` 即可。

## 6. 计算细节（两个必须写对的点）

### 6.1 通过率：BigDecimal 除法必须给精度

```java
BigDecimal rate = BigDecimal.ZERO;
if (approved + rejected > 0) {
    rate = BigDecimal.valueOf(approved)
            .divide(BigDecimal.valueOf(approved + rejected), 2, RoundingMode.HALF_UP);
}
```

`divide(divisor)` 不传 scale 时，遇到除不尽（如 1/3）会抛 `ArithmeticException: Non-terminating decimal expansion`。

### 6.2 平均耗时：null 与单位

```java
Double avgMinutes = reportMapper.avgApprovalMinutes();   // 没有数据时返回 null
BigDecimal avgHours = avgMinutes == null ? BigDecimal.ZERO
        : BigDecimal.valueOf(avgMinutes)
                  .divide(BigDecimal.valueOf(60), 1, RoundingMode.HALF_UP);
```

- `AVG` 在没有匹配行时返回 `null`，必须判空；
- SQL 里算分钟、Java 里转小时，避免 SQL 做小数除法又踩精度问题。

## 7. 失败与边界

| 情况 | 表现 | 处理 |
|---|---|---|
| 缺 `X-User-Id` | `40001` | Controller 判空 |
| 库中没有任何单 | 全部返回 0，`approveRate=0` | 不抛异常、不返回 null |
| `payment_order` / `reconcile_diff` 空表 | 对应计数为 0 | `selectCount` 天然返回 0 |
| 查询异常 | `50001` | 交给 `GlobalExceptionHandler` |

## 8. 验收

```powershell
curl -H "X-User-Id: 6" http://127.0.0.1:8080/api/v1/admin/metrics
```

对照 SQL 手工核一遍：

```sql
SELECT status, COUNT(*) FROM expense_report WHERE deleted = 0 GROUP BY status;
SELECT status, COUNT(*) FROM payment_order GROUP BY status;
SELECT status, COUNT(*) FROM reconcile_diff GROUP BY status;
SELECT status, COUNT(*) FROM outbox_message GROUP BY status;
```

验收标准：

1. 三个计数与 SQL 完全一致；
2. 通过率 = `approved / (approved + rejected)`，手算对得上；
3. 平均耗时与手工算的分钟数 / 60 一致（允许 0.1 的舍入差）；
4. 缺 header 返回 `40001`。

## 9. 扩展方向（现在不做，面试可讲）

- **缓存**：指标 60 秒内可容忍过期，接 Redis 缓存（`metrics:overview`，TTL 60s），避免每次 7 条 SQL；
- **预计算**：数据量大时，定时任务把每天的数字写进 `metrics_daily`，接口只查一行；
- **监控告警**：`outboxDead > 0` 或 `reconcileOpenDiffs` 连续两天增长 → 告警；
- **接入 Micrometer + Actuator**：暴露 JVM/HTTP 指标，但业务指标仍建议走本项目这套聚合，语义更清楚。

## 11. 常见坑

1. **漏 `deleted = 0`**：逻辑删除的单被算进统计，数字虚高。
2. **通过率分母用错**：拿「通过数 / 全部提交」会把在途单算进去，数字偏低。
3. **`BigDecimal.divide` 不传精度**：除不尽直接抛异常，接口 500。
4. **`AVG` 没判 null**：空表时 NPE。
5. **每次请求算 7 条 SQL 还全表扫**：数据量上来要做缓存/预计算，别指望索引。
6. **把指标接口写成写操作**：它是只读看板，不要在这里「顺手」补数据。

---

## 12. 面试表述

> 运营指标接口聚合提交数、通过率、平均审批时长、待付款、对账差异和 MQ 死信数，全部实时读现有表；通过率按「已出结果的单」计算，避免在途单稀释；平均时长在 SQL 里取分钟、Java 里转小时，规避小数精度问题。数据量上来后计划加 60 秒 Redis 缓存或按天预计算，而不是给 COUNT 加索引。
