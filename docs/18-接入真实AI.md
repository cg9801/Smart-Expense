# 18 接入真实 AI（从 mock 切到真模型）

> 现状：两条 AI 链路默认都走 **mock**，不需要任何 key 也能跑通全流程与测试。
> 本文只讲"怎么换成真模型、怎么验证、花了多少钱、坏了怎么办"。
> 代码位置：AI 审核 `ai/QwenChatClient`，发票识别 `invoice/QwenVlInvoiceRecognizer`，配置在 `application.yaml`。

## 1. 先分清两条线

| 链路 | 用在哪 | 默认实现 | 真实实现 | 开关 |
|---|---|---|---|---|
| AI 审批建议（Agent） | 提交后异步算风险建议 | `MockAiChatClient` | `QwenChatClient`（qwen-plus，文本） | `ai.provider=qwen` |
| 发票识别 | 上传后异步抽字段 | `MockInvoiceRecognizer` | `QwenVlInvoiceRecognizer`（qwen-vl-max，多模态） | `INVOICE_QWEN_ENABLED=true` + `INVOICE_RECOGNIZER_PRIMARY=qwen-vl` |

> **默认的 mock 不是 OCR**：`MockInvoiceRecognizer` 按文件内容哈希派生票号/金额/日期，同一张图结果稳定，但它是**确定性假数据**，不会真的读发票。前端会显示「演示数据，非真实识别」，复核页也会提示。看到金额不合实际，先确认 `recognizer` 是不是 `mock`（`GET /invoices/{id}` 或复核列表的「识别器」列）。

两条线都遵守同一条铁律：**模型只写自己的表**（`ai_review` / `invoice`），不碰报销单状态、不自动通过。

## 2. 准备工作（一次性）

1. 到阿里云百炼控制台开通模型服务，创建 API Key；
2. 只通过环境变量注入，**不要写进 `application.yaml` 或提交到 git**：

```powershell
$env:DASHSCOPE_API_KEY = 'sk-xxxxxxxx'
```

3. 确认能连通（PowerShell）：

```powershell
curl.exe "https://dashscope.aliyuncs.com/compatible-mode/v1/models" `
  -H "Authorization: Bearer $env:DASHSCOPE_API_KEY"
```

> 项目用的是 DashScope 的 **OpenAI 兼容接口**（`/chat/completions`），换其他厂商只要兼容这个协议，改 `ai.base-url` 即可。

### 2.1 设了环境变量却还是 mock？先看这三条

**环境变量只对"启动后端的那个进程"生效。** 在 PowerShell 里 `$env:...` 只影响当前终端；IDEA 是另一个进程，不会继承。

| 启动方式 | 变量放哪 |
|---|---|
| IDEA 绿色三角 | Run Configuration → Environment variables 里加，或改 `application.yaml` |
| 终端 `mvnw spring-boot:run` | 必须在**同一个终端**先 `$env:...` 再启动 |
| 想要一劳永逸（本地） | 用户级变量：`setx INVOICE_QWEN_ENABLED true`，然后**重开终端/IDE** |

> 项目里已经放了一个 IDEA 运行配置：`.idea/runConfigurations/SmartExpenseApplication_qwen.xml`
> （名字 `SmartExpenseApplication (qwen)`，已带三个环境变量与占位 key）。IDEA 重启/刷新后会出现在 Run Configurations 下拉里，把 key 填上即可，不用每次手动配。

**自检顺序**：

1. 重启后看启动日志：
   - `发票识别链：primary=qwen-vl, 已注册实现=[mock, qwen-vl]` → 配置生效；
   - `已注册实现=[mock]` + WARN「primary=qwen-vl 但 qwen-vl 未注册」→ 变量没进到进程里；
   - `当前主识别器是 mock` → primary 没设成 qwen-vl。
2. 上传后查 `GET /api/v1/invoices/{id}`：`recognizer` 字段是 `qwen-vl` 才算接上。
3. 确认三个变量都齐：`INVOICE_QWEN_ENABLED=true`、`INVOICE_RECOGNIZER_PRIMARY=qwen-vl`、`DASHSCOPE_API_KEY`。

### 2.2 已验证的坑：qwen 客户端启动失败

2026-10-31 实测：`QwenChatClient` / `QwenVlInvoiceRecognizer` 原先注入 `RestClient.Builder`，但本项目没有 webclient starter，容器里没有这个 Bean → 一旦 `ai.provider=qwen` 或 `INVOICE_QWEN_ENABLED=true` 就 **APPLICATION FAILED TO START**（`No qualifying bean of type RestClient.Builder`）。

已修复：两个客户端都改成 `RestClient.builder()` 自建，不依赖容器。若你在旧分支上看到这个错，按同样方式改。

## 3. 启用 AI 审批建议（文本模型）

```powershell
$env:AI_PROVIDER = 'qwen'
$env:AI_TEXT_MODEL = 'qwen-plus'
cd Smart-Expense
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-25.0.4.1'

```

验证：

1. 登录 `linyi` 建单提交；
2. 等 2–10 秒（Outbox → MQ → ai-review-consumer）；
3. `GET /api/v1/reports/{id}` 返回 `aiAdvice.model = "qwen-plus"`（mock 时是 `"mock"`）；
4. 审批页看到建议；断网/写错 key 时页面显示「暂无 AI 建议」，审批照常。

## 4. 启用发票识别（多模态模型）

```powershell
$env:INVOICE_QWEN_ENABLED = 'true'
$env:INVOICE_RECOGNIZER_PRIMARY = 'qwen-vl'
$env:INVOICE_RECOGNIZER_FALLBACK = ''        # 生产建议留空：主实现失败就 MANUAL，不拿 mock 假数据顶
$env:AI_VL_MODEL = 'qwen-vl-max'
```

验证：

1. 上传一张**真实发票图片**（jpg/png）；
2. 前端票据页/接口 `GET /api/v1/invoices/{id}` 轮询：
   - `ocr_status`：`PENDING → PROCESSING → SUCCESS`（低置信度会变 `MANUAL`）；
   - `recognizer`：`qwen-vl`；
   - `fields[]` 有每字段置信度，`confidence` 是整单值；
3. 复核队列（财务登录 `/invoices`）能看到 `MANUAL` 的发票，人工修正后置 `SUCCESS`。

### 4.1 降级链怎么配

`InvoiceRecognizerChain` 按 `primary → fallback` 顺序调用，全失败才 `FAILED`：

| 场景 | 推荐配置 | 结果 |
|---|---|---|
| 本地开发 / 压测 | `primary=mock` | 不出网、不花钱 |
| 真实演示（要真实字段） | `primary=qwen-vl`，`fallback=` 空 | 模型挂了 → `MANUAL`，人工接手 |
| 想按"先真后假"演示降级 | `primary=qwen-vl`，`fallback=mock` | 主实现失败会拿 mock 假字段，**仅演示用，别用于真实业务** |

### 4.1.1 模型名（2026-10 实测）

| 模型 | 结果 |
|---|---|
| `qwen3-vl-plus` | ✅ 可用（默认已改为它） |
| `qwen-vl-ocr` | ✅ 可用（偏表格 OCR，输出结构不同） |
| `qwen-vl-max` | ❌ `model_not_found`（已下线/改名） |

模型名会随平台迭代变化，接之前先用 `/models` 查一遍：

```powershell
curl.exe "https://dashscope.aliyuncs.com/compatible-mode/v1/models" -H "Authorization: Bearer $env:DASHSCOPE_API_KEY"
```

看到 `model_not_found` 就换一个：设 `AI_VL_MODEL=qwen3-vl-plus` 重启即可，不用改代码。

> **真实识别验证（2026-10-31）**：同一张 99 号发票（广东省医疗门诊收费票据），`qwen3-vl-plus` 返回 `SUCCESS`、金额 **138.43**、日期 **2026-08-31**，`recognizer=qwen-vl`。说明链路、prompt、JSON 解析都能跑通。

### 4.1.2 别同时跑两个后端实例

两个实例连同一个库、同一个 RabbitMQ 队列，会**抢同一条识别消息**：

- 旧实例（配置还是旧模型名）抢到 → `404 Model not exist` → 发票 `FAILED`；
- 新实例抢到 → 正常识别。

表现就是"明明改了配置还是失败"。排查时先确认**只有一个后端在跑**：

```powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen | Select-Object OwningProcess
```

## 5. 接其他模型（OpenAI / 豆包 / 本地 Ollama）

只要接口兼容 OpenAI 的 `/chat/completions`：

```yaml
ai:
  base-url: ${AI_BASE_URL:https://api.openai.com/v1}
  api-key: ${DASHSCOPE_API_KEY:}
  text-model: gpt-4o-mini
  vl-model: gpt-4o
```

**不兼容怎么办**：实现一个 `InvoiceRecognizer`（`name()` + `recognize()` 返回 `RecognitionResult`），注册成 Spring Bean，再把 `primary` 改成你的名字即可——识别链路、状态机、复核队列都不用动。

## 6. 接云 OCR（阿里云/腾讯云 OCR）

设计上云 OCR 是"主实现"（字段准、便宜），但本项目没有内置厂商 SDK。接法：

1. 新建 `CloudOcrInvoiceRecognizer implements InvoiceRecognizer`：
   - 调厂商 OCR 拿全文 + 字段；
   - 映射成 `RecognitionResult`（字段 + 每字段置信度 + 原始 JSON）；
2. `app.invoice.recognizer.primary=cloud-ocr`，`fallback=qwen-vl`；
3. 云 OCR 返回字段缺失时抛 `RecognitionException`，链会自动降级。

## 7. 成本护栏（别让演示账单失控）

| 护栏 | 位置 | 说明 |
|---|---|---|
| `file_hash` 复用 | 上传 | 同人同图不再调模型（docs/11 §3.4） |
| 单次超时 | `app.invoice.recognizer.timeout-ms=20000` | 超时算失败，转下一实现或 MANUAL |
| 整单置信度阈值 | `app.invoice.confidence-threshold=0.85` | 低于阈值不自动用，进复核 |
| 压测/测试 | 一律 mock | `mvn test` 全程不出网、不产生费用 |
| 每日调用上限 | **未实现**（规划中） | 建议按 `invoice.created_at` 统计当天识别次数，超限直接 MANUAL |

## 8. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `缺少 ai.api-key` | 没设 `DASHSCOPE_API_KEY` | 设环境变量后重启 |
| 401 / `InvalidApiKey` | key 错或没开通模型 | 控制台确认模型已开通 |
| `模型输出不是合法 JSON` | 模型没按 JSON 返回 | 已带 `response_format=json_object` + prompt 约束；仍失败会落 `FAILED`，可手动重试 |
| 发票一直 `PENDING` | Outbox 没投递 / MQ 没起 | 看 `outbox_message` 状态；`docker compose ps` 确认 RabbitMQ |
| 跨人上传同图被允许 | 索引已改 `(uploader_id, file_hash)` | 正常行为，`duplicateSuspect=true` 提示疑似重复报销 |
| 复核后字段又被覆盖 | 不会 | 回写条件 `WHERE ocr_status='PROCESSING'`，人工复核结果不会被重复消息覆盖 |
