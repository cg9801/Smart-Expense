# 20 压测报告（只读链路）

> 数据来源：`scripts/load-test.mjs` 在本地单机实测，**不是 JMeter**，也不是生产环境。
> 结论只代表“当前演示环境 + 默认 mock 识别”下的只读接口表现，不对外宣称生产容量。

## 1. 结论（2026-10-31 14:45）

| 场景 | 请求数 | 成功 | 错误率 | QPS | P50 | P95 | P99 |
|---|---|---|---|---|---|---|---|
| `GET /reports`（列表） | 4055 | 4055 | 0% | **270.33** | 10.5 ms | **15.3 ms** | 21.2 ms |
| `GET /reports/{id}`（详情） | 4054 | 4054 | 0% | **270.27** | 25.1 ms | **34.4 ms** | 47.2 ms |

- 并发 10、持续 15 秒、两个场景交替压；
- 全程 0 错误，没有超时（脚本默认 fetch 无超时，实际均 < 100ms）；
- 详情比列表慢约 2 倍：详情要多查明细、审批链、发票、AI 建议，符合预期。

## 2. 环境与方法

| 项 | 值 |
|---|---|
| 机器 | 本机 Windows（单机，Docker 跑 MySQL/Redis/RabbitMQ） |
| 后端 | Spring Boot 4.1.1 / JDK 25 / Tomcat 11 |
| 数据库 | MySQL 8（Docker，映射 3307），无缓存 |
| 前端 | 不参与压测（纯 API） |
| 识别 | 默认 `mock`（压测不出网、不产生模型费用） |
| 工具 | `scripts/load-test.mjs`（Node 24 原生 fetch，自统计延迟） |

```bash
# 复现
node scripts/load-test.mjs --base http://127.0.0.1:8080 --concurrency 10 --duration 15
```

脚本逻辑：
1. 登录 `linyi` 拿 JWT；
2. 拉一页列表拿一个真实 `reportId`；
3. 10 个 worker 在 15 秒内交替请求「列表 / 详情」；
4. 按场景统计 QPS、P50/P95/P99、错误率。

## 3. 解读

- **瓶颈在数据库查询与 JSON 序列化**，不在框架层：列表与详情都是同步 SQL，单机 MySQL 足够撑这个量级；
- **列表比详情快**：列表只查主表 + 申请人姓名，详情还要查明细/审批链/发票/AI 建议（4–5 条 SQL）；
- **没有缓存**：docs/10 已说明数据量小、不加 Redis；如果要做高并发，先给列表/详情加 Redis 缓存并接受“秒级不一致”，再考虑读写分离。

## 4. 局限（面试要主动说）

1. **只读链路**：提交/审批/上传/识别等写路径未压；写路径的瓶颈会落在行锁、条件更新与 MQ，而不是这里的 QPS；
2. **单机 + Docker MySQL**：没有独立 DB、连接池也不是生产配置（Hikari 默认 10）；
3. **mock 识别**：识别走本地 mock，不代表接真实 qwen-vl 后的耗时（真实模型单张 1–5s，且已异步，不影响主接口）；
4. **没有对比基线**：要讲“优化前后”需要再压一次带缓存的版本。

## 5. 建议的下一步压测（如果要做写路径）

| 场景 | 关注点 | 预期风险 |
|---|---|---|
| 并发提交同一单 | `submit_token` 幂等、`uk` 冲突回放 | 冲突重试率 |
| 多人同时审批同一级 | 行锁等待、死锁 | 死锁/超时 |
| 批量上传发票 | multipart IO、Outbox 投递 | 磁盘/MQ 堆积 |
| 对账任务与业务并发 | 行锁竞争 | 锁等待 |
